Generative AI now takes part in most stages of research, from reading the literature to writing and analysing. Each of its replies is a sample. A language model builds a reply by drawing one token at a time from a probability distribution, so the same request can return a different reply (Holtzman et al., 2020). The model behind a product name is also updated over time (Chen et al., 2024). Reproducibility, in the sense set out by the National Academies of Sciences, Engineering, and Medicine (2019), means obtaining consistent results from the same input data, computational steps, methods, code and conditions of analysis. A reply in a chat window meets few of those conditions. Its computations happen out of view, the settings that shaped it are rarely shown and the next reply to the same request may differ.

Agentic tools work differently. Claude Code reads a project, edits its files and runs commands in the researcher’s own environment (Anthropic, n.d.-b). ChatGPT Work acts across a user’s apps and files and turns a goal into finished documents, spreadsheets and web apps (OpenAI, 2026). When such a tool writes an R or Python script, the variability of the model enters while the script is being written. Once the script is saved, the analysis is as deterministic as any other code. It can be read, tested, kept under version control and executed again.

This post examines that division of labour with an experiment. I gave one analysis request, about a simulated semantic-priming data set, to 48 independent Claude Code agents. Half of them answered in prose, as a chat assistant without a code interpreter would, and half wrote an R script that I then executed. The data come from my pilotr package (Bernabeu, 2026b), which generates identical data from a design specification in R and in Python. The results bear on two questions: where the determinism of an AI-assisted analysis comes from, and what the researcher needs to know of R and of an integrated development environment (IDE) to keep it.

Development

This section reviews the sources of variation in the output of language models and the case for moving computation into code. It then describes the data and the design of the experiment.

Where the Variation Comes From

Setting the sampling temperature to zero, which should select the most probable token at every step, does not make hosted models deterministic. When Ouyang et al. (2025) asked ChatGPT to write code for 829 programming problems, the code returned by repeated requests never produced the same test output for between 47.56% and 75.76% of the problems, depending on the benchmark. A temperature of zero reduced that variation without removing it. Atıl et al. (2025) ran five hosted models 10 times on each of eight tasks with settings meant to be deterministic and found that accuracy varied by up to 15% across runs. He and Thinking Machines Lab (2025) traced much of this behaviour to the inference server. The number of requests processed together changes with the load on the server, and kernels whose floating-point arithmetic depends on that number change the result. In their test, 1,000 completions of one prompt at temperature zero contained 80 distinct texts, and kernels made invariant to the batch size brought them down to one. Anthropic’s documentation states that results will not be fully deterministic even at temperature zero (Anthropic, n.d.-a), and its most recent models reject any temperature other than the default (Anthropic, n.d.-c). For users of those models, the setting has left their control altogether.

Sampling is one source of variation among several. Chen et al. (2024) compared the March and June 2023 versions of the two models behind ChatGPT on the same tasks and found substantial changes in behaviour within three months. One of them identified prime numbers with 84% accuracy in March and 51% in June. The format of a prompt matters too. Changes in prompt formatting that preserve meaning altered the accuracy of one open model by up to 76 percentage points in few-shot tasks (Sclar et al., 2024). When models annotated text for hypothesis tests, the choice of model and prompting strategy led to incorrect conclusions for about one in three hypotheses with state-of-the-art models (Baumann et al., 2025). The providers of closed models can also change them at any time (Spirling, 2023), which is one reason why Palmer et al. (2024) argue that research using them needs explicit justification. In a chat interface, none of these sources is under the user’s control, and few are recorded.

Moving the Computation Into Code

The practices of reproducible computational research ask that every result be traceable to the steps that produced it and that no step be manual. They also ask that scripts be kept under version control, that the versions of external programs be archived and that random seeds be recorded (Sandve et al., 2013; see also Peng, 2011; Wilson et al., 2017). A script written by an agent into a project under version control is such a record. The variability of the model does not disappear, since a second request would yield a different script, but it is confined to the writing of the script, where the researcher can inspect it. The software environment still has to be kept. When Trisovic et al. (2022) re-executed R files deposited with published research data, 74% failed to complete without error, and 56% still failed after automatic code cleaning. A lockfile from renv (Ushey & Wickham, 2026) and a record of the R session reduce that risk.

The data set used in the experiment illustrates the same principle on a small scale. pilotr stores a design as a portable specification and draws its random numbers from its own generator, so the same specification and seed produce the same data in R and in Python (Bernabeu, 2026b). The specification describes 30 participants who each respond to 24 words, once after a related prime and once after an unrelated one. Reaction times follow a shifted lognormal distribution, with by-participant and by-item random intercepts and priming slopes and a word-frequency covariate.

The three checksums are identical, so the data set can be rebuilt byte for byte in either language from a few lines of JavaScript Object Notation (JSON). Because the data are simulated, the size of the priming effect in the population they come from is also known. For a shifted lognormal response, the mean reaction time in each condition follows from the parameters of the specification, as the next chunk shows.

# The mean of a lognormal variable is exp(mu + variance / 2). Here the
# variance gathers the frequency covariate, the random intercepts and slopes
# (with their covariance, which depends on the condition) and the residual.
population_mean <- function(spec, prime_code) {
  fixed <- spec$fixed; random <- spec$random; frequency <- spec$predictors[[1]]
  subject <- random$subject; item <- random$item
  covariance <- subject$intercept_sd * subject$slopes$prime_c *
    subject$correlations[['intercept,prime_c']] +
    item$intercept_sd * item$slopes$prime_c * item$correlations[['intercept,prime_c']]
  variance <- (fixed$coefficients$frequency * frequency$sd)^2 +
    subject$intercept_sd^2 + item$intercept_sd^2 +
    prime_code^2 * (subject$slopes$prime_c^2 + item$slopes$prime_c^2) +
    2 * prime_code * covariance + spec$response$sigma^2
  spec$response$shift + exp(fixed$intercept + fixed$coefficients$frequency * frequency$mean +
                              fixed$coefficients$prime_c * prime_code + variance / 2)
}
population_effect <- population_mean(spec, 0.5) - population_mean(spec, -0.5)
sample_effect <- with(regenerated, mean(rt[prime == 'unrelated']) - mean(rt[prime == 'related']))
c(population = population_effect, sample = sample_effect)

Forty-Eight Runs of One Request

design <- read.csv(file.path(experiment, 'design.csv'))

Every run received the same description of the data and the same question: ‘How large is the priming effect, that is, how much slower are responses after unrelated primes than after related primes? Give the estimate in milliseconds with a 95% confidence interval.’ The runs differed in three respects. The request was either open, leaving the analysis to the agent, or specified, naming the model, the coding of the predictor and the method for the interval. The route was either prose or a script. In the prose route, the agent could read the data file but was told to run no code and to answer in its reply, as it would in a chat without a code interpreter. In the script route, the agent wrote an R script and could run it to check its work. Every run had to end with a line in a fixed format giving the estimate and the interval, so that the answers could be compared by code. Most runs analysed the balanced data set described above. In a follow-up, the specified request was also given with an unbalanced version of the data, described in the Results, together with one added sentence saying that incorrect responses had been removed.

The prompts, like everything else in the experiment, are stored with this post. The specified request, as one of the script runs received it, reads as follows. The open request lacks the paragraph that begins ‘Analyse the data as follows’.

The design has 8 runs in each combination of condition and route, 48 in total, launched on 29 September 2026 in a random order across conditions. Each run was an independent Claude Code agent (Claude Code 2.1.284), which inherited the model and reasoning settings of the session that launched it and worked in its own directory, holding only the data file. The agents were launched from a Claude Code session, which also collected their outputs and executed the scripts. The logs of their tool calls show that 48 of the 48 runs kept to their instructions: no prose run used any tool other than reading its data file, and no script run touched a file outside its own directory. I executed each final script three times, each time in a fresh R process and a fresh copy of its directory, and this page executes every script once more when it is built.

Results

The results cover the agreement between runs, the accuracy of the prose replies, the follow-up with unbalanced data, the re-execution of the scripts and the time each route took.

The open request left every analytic decision to the agents, and the eight scripts converged on one analysis. Each fitted a linear mixed-effects model to the untransformed reaction times, with crossed random effects for participants and words. Each found that the maximal model was singular, because the priming effect barely varied across participants, and dropped the by-participant slope. All eight then computed the interval from a t distribution with Satterthwaite degrees of freedom. Four of them also included word frequency as a covariate, which cannot change the estimate in a balanced design, since every word appears in both conditions. The prose replies reached the same interval by another path. They decomposed the 720 paired differences into participant, item and residual components, and in a balanced design that decomposition gives the same standard error as the reduced model. With the specified request, both routes returned the Wald interval of the maximal model.

Of the 32 agents working on the balanced data, 14 mentioned in their replies the narrower interval of a simpler analysis. A paired t test over the participants’ mean differences gives an interval of [5.6, 31.5] ms, which excludes zero, because it ignores the variation of the priming effect across words. An analysis that leaves out how an effect varies across items overstates the evidence for generalising beyond the items sampled, which is why Barr et al. (2013) recommend the maximal random-effects structure that the design justifies. The agents set the paired analysis aside. They need not have agreed so closely with one another. When 29 teams analysed one data set to answer one question, their odds ratios ranged from 0.89 to 2.93, and 20 of the 29 teams found a statistically significant effect (Silberzahn et al., 2018). When 70 teams tested the same hypotheses on one neuroimaging data set, no two of them chose the same workflow (Botvinik-Nezer et al., 2020). Coding agents can show the same diversity. Autonomous AI analysts given one data set and one hypothesis reached divergent verdicts in three domains, and their conclusions shifted with the model and the prompt (Bertran et al., 2026). Alizadeh et al. (2026) ran Claude Code and Codex 20 times each on a many-analysts study of immigration and social policy. The agents varied their model specifications at least as much as the human teams had, while their estimates stayed broadly in line with the human consensus. On the simpler task in this post, one model in one session made the same choices eight times out of eight. A different model, version or wording could choose differently, and the interval would move with the choice.

Each value in Table 2 appears, exactly as R gives it, in at least 7 of the 16 replies. The balance of the design is what made this possible. With every participant seeing every word in both conditions, the restricted maximum likelihood (REML) solution of the model can be written in closed form. The replies to the specified request derived it by hand, down to the singular by-participant covariance matrix that lme4 reports (Bates et al., 2015). The cost of that route shows in Figure 2 below.

When the Design Is Unbalanced

The follow-up removed 86 of the 1,440 trials at random, as if they had been errors, which leaves some participant-word pairs with one condition only. Without balance, the estimate of the mixed model no longer equals the difference between the condition means, which is 21.43 ms, and the REML fit has to be found numerically. The eight scripts printed the same result, an estimate of 21.79 ms with an interval of [0.58, 43.00] ms.

The prose replies approximated the model with weighted averages of the per-word effects and estimates of the variance components from the observed mean squares. Table 3 sets their results beside the executed one.

Discussion

The discussion considers where the determinism came from and what the researcher contributes, and outlines a workflow that follows from the results before turning to the limits of the experiment.

Where the Determinism Came From

No text in this experiment was ever repeated, while every executed script gave the same output each time it ran. The determinism came from executing code. Even the agreement of the prose replies with the scripts could only be established by code: without recomputing their quantities in R, a correct reply could not be told apart from a confident error. On balanced data, the model’s arithmetic over 1,440 rows was reliable, which is a notable result in itself. It was also slow, and on unbalanced data, where the analysis has no closed form, it could only approximate, with a different approximation each time.

The results also qualify the studies reviewed above. Those found large variation from one request to the next in code generation and in benchmark accuracy (Atıl et al., 2025; Ouyang et al., 2025). Here, the agents converged on the same analysis and the same numbers whenever the question was well posed. Specifying the analysis removed the remaining choices, in line with the finding of Bertran et al. (2026) that a published specification reveals how much of the disagreement between AI analysts comes from underspecified design choices. The variation lay in the wording, which does not matter for a result, and in secondary choices such as a covariate that could not affect the estimate. That consistency belongs to one model on one structured task on one day, and the reproducibility of a study cannot rest on it. A script can be checked, whereas the consistency of a model can only be observed, and it may not survive the next update (Chen et al., 2024).

Why Direct Experience With R and an IDE Matters

The specified request is where expertise entered the experiment. Writing it required knowing that the data call for crossed random effects and that the random slopes included change the interval (Barr et al., 2013). It also required knowing that transforming reaction times can change the effects being tested (Lo & Andrews, 2015), that a singular fit is an estimate on the boundary of the parameter space and that a Wald interval differs from one based on Satterthwaite degrees of freedom. Given that request, every script returned the same result in under a minute. Without it, the agents made those decisions themselves. They decided defensibly, but the decisions were theirs, and a simpler analysis of the same data would have reported an effect that the mixed models did not support.

Reading the code is the second point of entry. The scripts in this experiment ran from 30 to 143 lines. A researcher who reads R can confirm in a few minutes that a script fits the intended model to the intended rows, and can spot a dropped random slope, a silent exclusion of trials or an unplanned transformation. An IDE makes those checks routine, with diffs of every change, version control, a view of the objects in memory and the option of running a script again in a fresh session. Without that experience, the researcher is left with the agent’s summary of its own work, which is another text generated by the same model.

Research on automation explains why this knowledge needs maintaining. Bainbridge (1983) observed that automation leaves its operators to monitor the system and to take over when it fails, while the skills needed for both deteriorate when they are no longer practised. Complacency towards automation occurs in experts as well as novices and is not overcome by simple practice (Parasuraman & Manzey, 2010). People’s impressions of AI assistance can also be wrong. In a randomised trial with 16 experienced open-source developers, allowing AI tools increased the time taken to complete tasks by 19%, although the developers believed afterwards that it had reduced it by 20% (Becker et al., 2025). In a survey of 319 knowledge workers, higher confidence in generative AI was associated with less self-reported critical thinking, and higher confidence in oneself with more (Lee et al., 2025). When software engineers learned a new programming library with or without AI assistance, those who used it scored lower on a subsequent test of their understanding of the library, with no significant gain in speed (Shen & Tamkin, 2026). Messeri and Crockett (2024) warn that AI tools can leave scientists believing that they understand more than they do. For early-career researchers in particular, the ability to check an agent’s code has to be built by writing code, and it is the ability that this workflow depends on.

A Reproducible Workflow With Coding Agents

The experiment suggests a workflow in which the project lives under version control, with a lockfile for its packages. The analysis plan is written before the agent writes any code, ideally in a preregistration, so that the request is a specified one. The agent writes scripts into files, and the researcher reads each diff before accepting it, runs the scripts in a fresh session and commits them together with their outputs. The prompts, the agent’s replies and a log of its tool calls are kept beside the scripts, as they are for this post. Where possible, the agent’s code is first tested on simulated data with known parameters, as pilotr allows, so that its ability to recover an effect is checked before it meets real data. Finally, some uses of a model process data directly, as in text annotation. There, a model whose version can be pinned, such as an open model run locally, is preferable to one that can change without notice (Palmer et al., 2024; Spirling, 2023).

Limitations

The experiment used one model, one version of Claude Code and one day. The agents ran concurrently as subagents of a single session in one container, and interactive use of the same tool may differ. The task was well posed and the data were simulated, whereas real analyses are messier and their requests less precise. The prose route imitated a chat without a code interpreter. Commercial chat assistants often run code in a sandbox, which narrows the contrast, although the code and its environment are seldom kept with the result. The byte-identical executions assume a stable software environment, and a different version of lme4 could reach a singular fit differently. Finally, with eight runs in each cell, the counts describe these runs and do not estimate rates.
