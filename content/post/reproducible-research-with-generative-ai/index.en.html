Ask a chat assistant the same statistical question twice, and you may get two different answers. A language model writes each reply one token (often a word or part of one) at a time, sampling from a probability distribution, so the same request can return a different reply (Holtzman et al., 2020). That matters now that generative artificial intelligence (AI) is used at many stages of research (Andersen et al., 2025). Reproducibility means obtaining consistent results from the same input data, computational steps, methods, code and conditions of analysis (National Academies of Sciences, Engineering, and Medicine, 2019, p. 46), and a reply in a chat window meets few of those conditions. Its computations happen out of view, and the settings behind it are rarely shown.

Coding agents promise a way around this. Agentic tools such as Claude Code can read a project, edit its files and run commands (Anthropic, n.d.-e). When such a tool writes an R or Python script, the model’s variability enters while the script is written. Once saved, the script stops varying. Given the same input, the same software environment and any random seeds it needs, it should give the same output. It can be read, tested, executed again and kept under version control, in a system such as Git that records each version of a project’s files.

I wanted to see how well that division of labour holds up, so I ran an experiment. In each of two rounds, one Claude Code session (a single conversation with the tool) put an analysis question to 48 agents, each a separate run of the language model working alone with Claude Code’s tools. The question concerned a semantic-priming data set simulated with my pilotr package (Bernabeu, 2026b), so the true effect was known in advance. Half of the agents answered in prose, as a chat assistant without a code interpreter (a tool for running code) would, and half wrote an R script that was then executed. The second round repeated the first with the effort level set to medium. The results speak to two questions: what executing code adds to an AI-assisted analysis, and how much R a researcher needs to know to specify, read and check an agent’s code, both now and as these agents improve.

Development

Before the experiment itself, it helps to see where the variation in a model’s replies comes from and which of its sources a researcher can control. The first two sections below review both, and the next two describe the simulated data and the runs.

Why the Same Request Gets Different Replies

The obvious suspect is the randomness of sampling, which the temperature setting controls. A temperature of zero should select the most probable token at every step, yet it does not make models served by their providers deterministic. Ouyang et al. (2025) asked ChatGPT at its default temperature to write code several times for each of 829 programming problems from three published sets with tests. For 47.56% to 75.76% of the problems, depending on the set, no two programs gave the same output on the problem’s tests, and a temperature of zero reduced that variation without removing it. Atıl et al. (2025) ran five such models 10 times on each of eight tasks with settings meant to be deterministic, and accuracy varied by up to 15 percentage points across runs.

He and Thinking Machines Lab (2025) traced much of this behaviour to the providers’ servers, where the number of requests processed together varies with demand. That number changes the order, and so the rounding, of some sums, enough to tip the choice between two almost equally probable tokens. With an open model, one that anyone can download and run, 1,000 replies to one request at temperature zero contained 80 distinct texts, and computations independent of that number brought them down to one. Models that reason before answering are especially exposed, since a rounding difference early in the reasoning can send it down another path and change the answer (Yuan et al., 2025). Anthropic (n.d.-c) states that results are not fully deterministic even at temperature zero. Its recent models reject any temperature but the default. From version 2026-10-21 of its application programming interface (API), which lets other programs send requests to its models, any request that sets the temperature is rejected, whatever the model (Anthropic, n.d.-g).

Sampling is only one source of variation. Providers can change proprietary models at any time (Spirling, 2023) and retire them, after which requests to them fail (Anthropic, n.d.-d). Between its March and June 2023 versions, GPT-4, one of the two models behind ChatGPT, fell from 84% to 51% accuracy in classifying numbers as prime or composite (L. Chen et al., 2024). Meaning-preserving changes in the format of a prompt, the text given to a model, altered the accuracy of one open model by up to 76 percentage points when the prompt included a few solved examples (Sclar et al., 2024). In a chat interface, none of these sources is under the user’s control, and few are recorded.

What the Researcher Can Still Control

Reproducibility with generative AI therefore rests on three choices left to the researcher: the tools, the requests made of them and the record of both. For the tools, McLoughlin et al. (2026) recommend open models, which can be run locally and so run again later, and, like Palmer et al. (2024), they ask that any use of a proprietary model be justified explicitly. An open model served by a company, however, may not match the published one. In summer 2024, 11 of 31 services offering Meta’s Llama models gave outputs whose distribution differed from that of the published model (Gao et al., 2025).

The choice of tools extends to their settings, such as the effort level, which sets how many tokens a model spends on reasoning, text and tool use. Its default differs between models, and Anthropic (n.d.-b) advises comparing levels on one’s own tasks rather than carrying a setting over from an earlier model. The second round of this experiment ran at medium effort, the level that the API applies to the model used here unless told otherwise, and its results suggest that the setting can change the outcome. The access route matters too, since a model may behave differently in a chat window and through an API (Feuerriegel et al., 2026). So does the agentic tool around the model. Nadgir et al. (2026) report on 39 tasks from CORE-Bench, a benchmark that asks agents to reproduce published results from the studies’ code and data. At the same effort level, OpenAI’s GPT-5.4 solved 94.9% of them within Codex, the company’s own agentic tool, and 51.3% within CORE-Agent, an agent built for the benchmark.

Requests to an agent can ask for a script in place of an answer, one that runs without manual steps, prints the result in a fixed format and sets any random seeds. They can also ask for a file that pins package versions, and set out tests of the expected behaviour before the code is written, as Bridgeford et al. (2026) recommend. What the agents return still needs checking. Vangala et al. (2026) asked three coding agents for programs in Python, JavaScript and Java that would run in a clean environment, with every dependency and its version listed. Of the 300 programs, 205 ran without intervention, and on average, they used 15 times as many packages at run time as they declared.

Asking for a script brings AI-assisted work under the standards of reproducible computational research. These ask that every result be traceable to the steps that produced it, without manual data manipulation, and that the versions of external programs be archived (Sandve et al., 2013; see also Peng, 2011; Wilson et al., 2017). An agent’s script under version control documents the steps behind a result, but not the software environment, from the operating system to the package versions. When Trisovic et al. (2022) re-executed R files deposited with published research data, 75% of those that did not time out stopped with an error. After automatic fixes for problems such as missing packages and file paths that exist only on the original computer, 60% still did. The R package renv (Ushey & Wickham, 2026) reduces that risk with a lockfile that records the versions of R and of a project’s packages. With the output of sessionInfo(), the lockfile shows what has changed when a script behaves differently elsewhere.

Reporting guidelines set out the rest of the record. The GUIDE-LLM checklist asks authors in the behavioural sciences to report, among other items, the provider, the exact model identifier, the date of access, the access route, the settings and the prompts (Feuerriegel et al., 2026). Guidelines for software engineering add the version of the agentic tool, a trace of its tool calls (its actions, such as reading a file or running a command) and every setting, defaults included (Baltes et al., 2026).

A Data Set With a Known Answer

To judge the agents’ answers, I needed data whose true effect was known. The pilotr package generates data in R and in Python from a design specification written in JavaScript Object Notation (JSON), a plain-text format independent of any programming language. Because it uses the same random-number generator in both languages, and this specification rounds reaction times to whole milliseconds, the same specification and seed produce identical data in both (Bernabeu, 2026b). The specification below describes a balanced design in which 30 participants each respond to 24 words, once after a related prime and once after an unrelated one. Reaction times follow a lognormal distribution shifted to start at 250 ms, with a word-frequency covariate and with by-participant and by-word random intercepts and priming slopes.

The three checksums are identical, so the data set can be rebuilt byte for byte in either language. Because the data are simulated, the specification gives the population priming effect, and the code below estimates how much it varies across participants and across words by drawing a million of each.

fixed <- spec$fixed; random <- spec$random; frequency <- spec$predictors[[1]]
# effect_sd() below moves frequency with the word, so it must vary by word
stopifnot(frequency$name == 'frequency', frequency$varies_by == 'item')
mu <- fixed$intercept + fixed$coefficients$frequency * frequency$mean

# The variance, at a given prime code, of the terms that belong to one unit
# (participant or item): its random intercept and slope and their covariance.
unit_variance <- function(unit, prime_code) {
  unit$intercept_sd^2 + prime_code^2 * unit$slopes$prime_c^2 + 2 * prime_code *
    unit$intercept_sd * unit$slopes$prime_c * unit$correlations[['intercept,prime_c']]
}
residual_variance <- (fixed$coefficients$frequency * frequency$sd)^2 + spec$response$sigma^2

# The mean of a lognormal variable is exp(mu + variance / 2), and the shift
# cancels out of the difference between the two types of prime.
population_mean <- function(prime_code) {
  spec$response$shift + exp(mu + fixed$coefficients$prime_c * prime_code +
    (unit_variance(random$subject, prime_code) + unit_variance(random$item, prime_code) +
       residual_variance) / 2)
}
population_effect <- population_mean(0.5) - population_mean(-0.5)

# The priming effect of one participant (or word), averaged over the other
# unit and the residual, for a million simulated participants (or words). A
# word's frequency belongs to the word, so for words it moves with the word's
# intercept and is not averaged out.
effect_sd <- function(unit, other, word = FALSE) {
  z <- matrix(rnorm(2e6), ncol = 2)
  rho <- unit$correlations[['intercept,prime_c']]
  intercept <- unit$intercept_sd * z[, 1]
  slope <- unit$slopes$prime_c * (rho * z[, 1] + sqrt(1 - rho^2) * z[, 2])
  averaged <- residual_variance
  if (word) {
    intercept <- intercept + fixed$coefficients$frequency * frequency$sd * rnorm(nrow(z))
    averaged <- spec$response$sigma^2
  }
  unit_mean <- function(prime_code) exp(mu + intercept + prime_code * (fixed$coefficients$prime_c + slope) +
    (unit_variance(other, prime_code) + averaged) / 2)
  sd(unit_mean(0.5) - unit_mean(-0.5))
}

Every run received a description of the data and the same question: ‘How large is the priming effect, that is, how much slower are responses after unrelated primes than after related primes? Give the estimate in milliseconds with a 95% confidence interval.’ Each run had to end with a result line giving the estimate and the interval in a fixed format, so that code could compare the answers. The request was either open, leaving the analysis to the agent, or specified, naming the model, the contrast coding of the prime and the function that computes the interval. The data were either the balanced data set or, in a follow-up with the specified request, an unbalanced version from which 86 of the 1,440 trials had been removed at random. The request for these data said that incorrect responses had been removed. These three combinations of data and request are the conditions of the experiment.

In each condition, the runs followed one of two routes. In the prose route, the agent could read the data file but was told to run no code, to answer as in a chat without a code interpreter and, if it could not compute the answer exactly, to give its best estimate. In the script route, the agent wrote an R script, which it could run to check its work, and ended with a brief summary of what the script does. Its instructions named lme4 (Bates et al., 2015), lmerTest (Kuznetsova et al., 2017), emmeans and dplyr among the installed packages.

The prompts are kept in the experiment’s folder with the data, the scripts, each run’s final reply and a log of its tool calls, but not the agents’ full transcripts. The folder’s README explains how to download it on its own and repeat each step. Below is the specified request as one of the script runs received it. Both rounds used the language model Claude Opus 5.5 (identifier claude-opus-5-5), with eight runs in each combination of condition and route. The first round ran on 29 September 2026 with Claude Code 2.1.284. Its 32 runs on the balanced data were launched eight at a time, in a random order across conditions. The 16 runs of the follow-up were launched afterwards, also in a random order.

The runs were meant to be independent, so each worked in a folder of its own. In the first round, each agent ran in the background alongside others, with the model and effort level of the session that launched it, and was pointed to a folder that held only the data file. The logs show that each prose run read nothing but its data file, and that 21 of the 24 script runs touched no file outside their own folder. The other three wrote exploratory R files under shared names such as explore.R to a temporary folder open to all the session’s agents. Each wrote and ran such a file within one command and read only its own data, so none appears to have run another’s code. One of them also read the output of a background R command from the folder where the session stores such output. The first eight agents were launched from the experiment’s own folder, which holds the pilotr specification, and their logs show no access to it.

The session then executed each final script three times, each time in a fresh R process (as after restarting R) and a fresh copy of its folder. It also recorded the versions of R, lme4, lmerTest and Matrix, the package that lme4 uses for its matrix computations.

The second round ran on 11 October 2026 with Claude Code 2.1.295, from one session in the Claude desktop app on Windows 11. Its 48 runs were launched in the order of the first round, eight at a time, with those on the unbalanced data once 31 of the 32 on the balanced data had finished. Their prompts were the first round’s, except for each run’s folder and, in the script route, the version of R (4.6.1 in place of 4.3) and the full path of Rscript. Every agent ran at medium effort, as the transcripts record. Two runs on the balanced data, a prose reply to the specified request and a script for the open request, were also made at xhigh effort, the level above high, under the same conditions on the same day. No agent of the second round touched a file outside its own folder.

# The numbers of each RESULT line as written, so that a reply's precision is
# kept (a reply's '22.0' is not the same claim as a script's '21.79')
result_numbers <- function(line) {
  regmatches(line, regexec('estimate=(-?[0-9.]+) lower=(-?[0-9.]+) upper=(-?[0-9.]+)', line))[[1]][-1]
}
# Each result line as the tables show it, 'estimate [lower, upper]'

  vapply(lines, function(line) {
    n <- result_numbers(line)
    sprintf('%s [%s, %s]', minus(n[1]), minus(n[2]), minus(n[3]))
  }, character(1), USE.NAMES = FALSE)
}

column_shares <- function(table, shares) {
  separator <- grep('^\\|[-:|]+\\|$', table)
  cells <- strsplit(sub('^\\|(.*)\\|$', '\\1', table[separator]), '|', fixed = TRUE)[[1]]

                                         ifelse(endsWith(cells, ':'), ':', ''), collapse = '|'), '|')
  table
}

# Of two marks too close to tell apart, the one standing for fewer runs is

lowered <- function(deviation, runs) {
  lower <- rep(FALSE, length(deviation))
  for (i in seq_along(deviation)[-1]) {
    if (deviation[i] - deviation[i - 1] < 0.05) {
      lower[if (runs[i] <= runs[i - 1]) i else i - 1] <- TRUE
    }
  }
  lower
}

What the Agents Chose When Left to Choose

Given the open request, the eight scripts converged on one analysis, a linear mixed-effects model of the untransformed reaction times with crossed random effects for participants and words. The maximal model, with by-participant and by-word priming slopes, gave a singular fit, in which a random-effect variance is estimated at zero or a correlation at ±1. Its by-participant slope was perfectly correlated with the intercept, and every script dropped that slope. All eight then computed the interval from a t distribution with Satterthwaite’s approximation of the degrees of freedom, which lmerTest adds to models fitted with lme4 (Kuznetsova et al., 2017). Four also included word frequency as a covariate, although in a balanced design it cannot change the estimate, since every word appears after both types of prime.

Dropping the by-participant slope follows the parsimonious strategy that Matuschek et al. (2017) defend on the grounds of power, and sits uneasily with the maximal structure that Barr et al. (2013) recommend. The choice rested on the sample, as it must with real data. In this sample, the maximal model puts the standard deviation of the priming effect at 8.9 ms across participants and 29.8 ms across words, the reverse of the order in the population (18.3 and 12.9 ms).

The prose replies to the open request reached the same interval as the scripts by decomposing the 720 paired differences into participant, word and residual components. In a balanced design, this decomposition gives the same standard error as the scripts’ model without by-participant slopes. Five of these replies equated their decomposition with the maximal model, although that model keeps a small by-participant slope and gives a slightly wider Satterthwaite interval, [−1.78, 38.82] ms. With the specified request, both routes returned the Wald interval of the maximal model, which is narrower than either Satterthwaite interval because it takes its critical value from the normal distribution.

Every prose reply to the open request, and six of the eight summaries of its scripts, mentioned the narrower interval of a by-participant analysis. A paired t test over the participants’ mean differences gives [5.58, 31.46] ms, which excludes zero, and the same test over the words’ mean differences reproduces the open-request scripts’ interval, [−1.53, 38.57] ms. All of those replies and summaries set the by-participant analysis aside because it ignores how the effect varies across words and so overstates the evidence for generalising beyond the words sampled. The effect is real in this simulation, so that test reached the right conclusion by an analysis too liberal for the purpose. A test of the mixed models at the .05 level would have missed the effect, although their intervals contain its population value of 21.8 ms.

Mixed Models by Hand

An agent that ran no code could still fit a mixed model, and the prose replies to the balanced data showed how. Because every participant saw every word after both types of prime, the restricted maximum likelihood (REML) fit of the mixed model reduces to a few mean squares and cross-products of the paired differences and of their sums. Cross-products are the counterparts of mean squares for covariances. Table 2 recomputes in R the intermediate quantities that recur across the replies. Where a reply does not state the residual mean square as R gives it, it rounds the value or gives the residual variance, which is half of it.

Where Hand Calculation Runs Out

Removing trials takes away the shortcut that balance provides. In the unbalanced data, 84 participant-word pairs are left with a trial after only one type of prime and 1 with no trial at all. Without balance, the estimate of the mixed model, 21.79 ms in all eight scripts, no longer equals the difference between the mean reaction times after the two types of prime, 21.43 ms. Nor does the REML fit reduce to mean squares and cross-products, so it has to be found iteratively. The removal also moved the lower bound of the specified Wald interval from −0.74 to 0.58 ms, so that the interval no longer included zero. With Satterthwaite degrees of freedom, as in the open-request scripts, the same model gives [−0.57, 44.15] ms, which still includes zero.

The prose replies approximated the model with weighted averages of the per-word effects and estimates of the variance components from the observed mean squares. Unlike the replies to the specified request on the balanced data, each put the variance of the by-participant slopes at or near zero. The fit that lme4 found kept a by-participant slope with a standard deviation of 6.7 ms, perfectly correlated with the intercepts. The replies’ results therefore lie closer to those of the model without by-participant slopes, 21.85 [0.77, 42.92] ms, than to the executed result (Table 3).

How Long Each Route Took

Code was also much the quicker route when the analysis was specified. The scripts given the specified request took a median of 0.7 minutes (Figure 2), and the prose replies 13.7 minutes on the balanced data and 14.6 on the unbalanced data. The difference is the work of computing by hand what each specified script computed in 2.4 seconds or less, R’s start-up included. The open request took the scripts longer, with a median of eight tool calls against five, because the agents compared several random-effects structures and ran checks of their own. These scripts took 2.1 to 7.0 minutes, overlapping the prose replies’ 5.8 to 6.4. The runs shared the session’s access to the language model and ran in batches, and three of the main runs were still going when the follow-up was launched. The durations therefore include some waiting and are best read as orders of magnitude.

A Second Round, at Medium Effort

Specifying the analysis kept the scripts on course. Given the specified request, all 16 scripts of the second round returned the first round’s results, 2 of them to four decimals (Table 4). The open request split them: three scripts kept the by-word priming slope and returned the first round’s interval, and five dropped both random slopes after singular fits, keeping random intercepts only. Their Satterthwaite interval, [3.63, 33.41] ms, excludes zero. None of the five fitted the model that drops only the by-participant slope. In that model, lme4 puts the standard deviation of the by-word slope at 29.8 ms, away from the boundary, so the fit did not require dropping it.

max_listed <- 5
results_cell <- function(lines) {
  if (n_distinct(lines) > max_listed) {
    numbers <- t(vapply(lines, result_numbers, character(3), USE.NAMES = FALSE))
    span <- function(j) {
      value <- as.numeric(numbers[, j])
      sprintf('%s&nbsp;to&nbsp;%s', minus(numbers[which.min(value), j]), minus(numbers[which.max(value), j]))
    }
    return(sprintf('%s results, with estimates %s, lower bounds %s and upper bounds %s',
                   stringr::str_to_sentence(count_text(n_distinct(lines))), span(1), span(2), span(3)))
  }
  counts <- table(lines)
  lower <- as.numeric(vapply(names(counts), function(line) result_numbers(line)[2], character(1)))
  counts <- counts[order(-counts, lower)]
  paste(gsub(' ', '&nbsp;', sprintf('%s (%d)', as_written(names(counts)), as.vector(counts)), fixed = TRUE),
        collapse = '<br>')
}

Executing the Scripts Again

Executing a script again where it first ran tests whether it is deterministic, and executing it elsewhere tests whether its output depends on the environment. Every execution below ran in a fresh R process in the C locale, the minimal set of conventions for language and characters that every system provides. Outputs are compared through a checksum of their lines without the line endings, which Windows and Linux write differently. Between them, the scripts load dplyr, emmeans, lme4, lmerTest and tidyr, and lmerTest calls pbkrtest in the three open-request scripts that also report Kenward–Roger degrees of freedom. The Kenward–Roger method, an alternative to Satterthwaite’s approximation, also adjusts the standard error.

The first round’s 72 stored executions ran under R 4.3.3 on the Linux system Ubuntu 24.04.4 with lme4 1.1-35.1, lmerTest 3.1-3 and Matrix 1.6-5. Every script printed identical output each time, including its model summaries and warnings. Ubuntu 24.04 still offers those versions, so a Dockerfile rebuilds the environment from them, taking the other packages from a dated snapshot of the same release. A Dockerfile is a recipe from which the program Docker builds a packaged copy of an operating system and its installed software. Executed in that rebuild on a fresh machine provided by GitHub, all 24 scripts printed the stored output, as verification.csv records.

The 25 scripts of the second round were each executed twice, in the R library their agents had used, with R 4.6.1 on Windows, lme4 2.0-1, lmerTest 3.2-1 and Matrix 1.7-5. Each printed identical output both times, ending with the result line its agent had reported.

Discussion

What Executing the Code Added

No text in this experiment was repeated, yet every executed script printed the same output each time it ran. Because the versions of R, lme4, lmerTest and Matrix were recorded and can still be installed, the first round’s scripts printed that output on another machine too. Under newer versions, their output changed only in formatting, in ways traced to lme4. The scripts also added exactness and a record that can be checked. On unbalanced data, which call for a numerical fit, every script returned the fitted result and each prose reply an approximation of it. When the analysis was specified, code was also the quicker route, with a median of 0.7 minutes for the scripts against 13.7 for the prose replies to the balanced data. Even where the replies matched the scripts, only recomputing their quantities could tell a correct reply from a confident error.

A reproducible analysis can still be a poor one (Leek & Peng, 2015). The five scripts of the second round that dropped both random slopes printed identical output each time they ran. Their interval excludes zero and, because the effect is real in this simulation, it points the right way. With real data, nobody could know that. Leaving out a by-word slope when the effect varies across words makes a test too liberal (Barr et al., 2013), so the same analysis would claim an effect more readily where none existed.

Agreement between runs is a separate matter. On balanced data, it was complete in the first round. In the second, at medium effort, the prose replies to the balanced data gave seven different results and the open-request scripts two, whereas every script given the specified request returned the first round’s result. The close agreement of the first round contrasts with the large variation between runs of the same request that the studies reviewed above found in code generation and in accuracy (Atıl et al., 2025; Ouyang et al., 2025).

Many-analysts studies, which give one data set and one question to many teams, find wide variation among human analysts too. In one, the odds ratios of 29 teams ranged from 0.89 to 2.93 (Silberzahn et al., 2018). Autonomous AI analysts given one data set and one hypothesis also reached divergent verdicts in three domains, and their conclusions shifted with the language model and the prompt (Bertran et al., 2026). Alizadeh et al. (2026) ran Claude Code and Codex 20 times each on a many-analysts study of immigration and social policy (Breznau et al., 2022). The agents varied their model specifications at least as much as the human teams had, but their estimates stayed broadly in line with the human consensus. The authors located the agents’ vulnerability in interpretation more than in estimation.

The task in this experiment was far simpler, with two types of prime, participants crossed with words and one obvious family of models. On balanced data in the first round, the agents varied only in wording and in secondary choices such as the frequency covariate. On unbalanced data, even the seven different results of the prose replies lay within 0.3 ms of one another. That consensus may be narrower than it looks, since runs of one model are not independent analysts. When Herdağdelen et al. (2026) left Claude Opus 4.8 to make the five decisions of an analysis with no preference assigned to it, it made the same five choices in 112 of 123 runs. Forty-eight runs of one model that agree may amount to one opinion stated 48 times.

Bertran et al. (2026) propose deploying AI analysts against a published specification to reveal how much disagreement comes from underspecified design choices. Here, the open request produced little disagreement in the first round, but in the second it divided the scripts over one random slope, which decided whether their interval excluded zero. The consistency of the first round belonged to one model, at one effort level, on one structured task, and may not survive the model’s next update (L. Chen et al., 2024). A study’s reproducibility therefore has to rest on what can be checked, such as a script and a record of its environment.

Where Coding Literacy Comes In

By coding literacy, I mean being able to read and write code well enough to tell what a script does. The experiment did not vary it, but it shows where literacy could come in, and at those points, much of what is needed turns out to be statistical knowledge.

The specified request is where the researcher’s knowledge entered the experiment. Writing it required knowing that the data call for crossed random effects, that the choice of random slopes changes the interval (Barr et al., 2013) and that transforming reaction times can change the effects being tested (Lo & Andrews, 2015). Interpreting the output required knowing what a singular fit means. Coding literacy came in only where the request named the function that fits the model, wrote the model in the formula notation of lme4 and gave the call to confint() that computes the interval. I cannot say how much that helped, since no condition stated the same analysis in plain statistical language.

The same request shows the limits of a specification. It fixed a Wald interval, which is too narrow with few participants or items (Luke, 2017). I chose it because one function call defines it exactly and so makes the scripts comparable. On the unbalanced data, that choice decided whether the interval excluded zero. An analysis for publication should request Satterthwaite or Kenward–Roger degrees of freedom, as computed in the open-request scripts. Across the two rounds, none of the 65 runs given the specified request mentioned either. On this point, the agents left to choose did better than my specification.

Reading the code is the second point of entry. The scripts in this experiment were 18 to 252 lines long, short enough for a researcher who reads R to confirm in a few minutes that each fits the intended model to the intended rows. In the first round, every summary of an open-request script reported dropping the by-participant slope and justified it by the fit of the maximal model. Weighing that justification against the chance that the effect varies across participants in the population, as it does in this simulation, takes knowledge the summary does not supply.

In the second round, five scripts dropped the by-word slope as well, and three of their summaries stated that both slope variances were at or near zero. A reader of R would notice that each of these scripts skipped the model with only the by-word slope. Printing the fits they discarded would show that every model with that slope put its standard deviation at about 30 ms. Without experience of R, the researcher is left with the agent’s summary of its own work, which is another text generated by the same language model. Even so, what a reader would catch here is a statistical choice written in code, since no result pointed to a coding bug.

A reader of R is not the only possible remedy, however. Given the same open request at xhigh effort, the one script I ran kept the by-word slope with nobody reading it. Three of the eight at medium effort did too, so this is only a hint that a setting may do part of a reader’s work. A second agent asked to review each script might do more, although runs of one model may share its preferences, and different models often err in the same way (Kim et al., 2025). The experiment did not test this.

Studies of how people use these tools complicate the picture. Anthropic, the maker of Claude Code, analysed about 400,000 sessions with it and concluded that the ability to steer the agent comes more from command of a domain than from the ability to write code (Hitzig et al., 2026). People in software-related occupations reached the study’s strictest measure of success, which requires evidence such as passing tests or committed work, in about 30% of their sessions, and people in other occupations in about 26%. Sessions in which the user was rated a novice at the task reached it 15% of the time, against 28–33% for higher ratings. The authors call these findings preliminary, since the ratings come from a model’s reading of the transcripts and they cannot tell whether the code was used afterwards.

Fluency in code also does not guarantee independent judgement. In another study from Anthropic, 50 professional analysts who regularly used Python or R carried out an analysis with Claude Code, whose preference on each decision was secretly set by a coin flip. On four decisions between two reasonable options, they went with the agent’s preference 86% of the time, and in an exploratory analysis, neither experience nor expertise predicted who did so (Herdağdelen et al., 2026). The preferences were strengthened on purpose, so these figures may overstate everyday influence. The agent may also have helped, since 3 of the 50 made serious errors, against 6 of the 11 less experienced analysts who chose to work without it. Neither study compares people who can read code with people who cannot, so neither settles the question.

Two others come closer. In a randomised trial at the consulting firm BCG, whose tasks were designed with help from OpenAI, 487 consultants attempted data-science tasks outside their expertise, and those given ChatGPT outscored those given other resources. Among the former, self-described competent coders came within about 5 percentage points of the firm’s data scientists on the coding and statistics tasks, whereas the group as a whole stayed 12 to 14 points below them (Wiles et al., 2026). Coding experience was not randomised, however, and the tool was a chat assistant. A small preprint tested a coding agent directly. Of 54 computing students who built a website, those given the agent produced a better first version than those given a chatbot and understood it less well. With the agent, their background in code no longer predicted the quality of that version or how well they could extend it unaided, but it still predicted their comprehension (Balepur et al., 2026). An agent may therefore mask differences in literacy without removing them. Reading code remains the most direct check available, but it may not stay the only one, and it is not sufficient.

What May Change by 2029

This experiment captures one model on 29 September 2026 and 11 October 2026. How long the need for coding literacy that it points to will last is increasingly uncertain. At the time of writing, even the best models need steering to keep a codebase healthy. Left to themselves in my own projects, they let documentation go out of date, leave stale files behind, contradict themselves from one file to another and write the same logic twice. Carlini (2026), who built a 100,000-line C compiler with 16 parallel agents, noted that ‘LLM-written code frequently re-implements existing functionality’ and assigned one agent to coalesce duplicate code and others to improve code quality and documentation. In SlopCodeBench, a benchmark in which agents repeatedly extend their own code, the code’s structure eroded in 77% of the runs, and quality guidance repeated at every step improved the starting point without slowing the decline (Orlanski et al., 2026). In open-source projects that adopted Cursor, an AI code editor, development sped up sharply but briefly, whereas static-analysis warnings and code complexity rose persistently and slowed it down in the longer term (He et al., 2026). Noticing these problems, and knowing to ask for them to be fixed, currently takes someone familiar with code.

Some steering has already gone. Two years ago, models often had to be told which tool to use for a given task. As late as April 2025, a guide from OpenAI advised reminding GPT-4.1 to use its tools and not to guess, one of three reminders that raised its internal score on a coding benchmark by close to 20% (MacCallum & Lee, 2025). In my experience, that is rarely necessary with the best models today. Anthropic’s guide now warns that instructions needed for earlier models can make current ones overuse their tools, although it still offers a prompt telling them to read code before answering about it (Anthropic, n.d.-f). Independent tests point the same way. Context files such as AGENTS.md, which carry standing instructions for a repository, did not generally raise agents’ success on real tasks and added over 20% to the cost, although the agents followed them. The authors still see a use for such files in stating unusual conventions (Gloaguen et al., 2026). Claude Code’s guide lists further advice that users can stop following, because ‘most were workarounds for something the model couldn’t reliably do yet, and the models have since caught up’ (Anthropic, n.d.-a).

The upkeep of code and documentation is not on that list yet, and Anthropic’s prompting guide still offers instructions to clean up temporary files and avoid hard-coding values to pass tests (Anthropic, n.d.-f). The same shift nonetheless seems to be under way, though on thinner evidence. In SWE-CI (J. Chen et al., 2026), a benchmark in which agents maintain real repositories over many rounds of change, each provider’s newer models always scored higher, with markedly larger gains among those released in 2026. Most models, however, still broke previously passing tests in over three quarters of the tasks. In a research note from the organisation METR, maintainers reviewing patches from successive models saw the step from Claude 4 Opus to Claude 4.5 Sonnet improve mostly code quality (Whitfill et al., 2026). Agents can also do much of this work when assigned it, as in Carlini’s project, although that took a carefully designed environment and the code stayed well short of an expert’s. I expect that by 2029, these chores will be built into the best models, as the choice of tools largely has been. A researcher will then no longer need to recognise a stale file to keep a project healthy.

That is a forecast, and it may prove wrong. A trend points that way: by METR’s measure, the length of software task that frontier models can complete half the time has doubled about every seven months since 2019 (Kwa et al., 2025), and about every four months since 2023 (METR, 2026a). In spring 2026, the Forecasting Research Institute asked its panels when a model would succeed 80% of the time at software tasks that take a person eight hours. The median expert answered 2030 and the median superforecaster 2028 (Forecasting Research Institute, 2026). Such forecasts have tended to run low. On one hard coding benchmark, the median expert expected 14% by the end of 2026, and models had reached 53.8% by May. The record on adoption is more mixed, however, and a check made before the deadlines favours finding underestimates (Rosenberg et al., 2026).

METR’s measure has limits of its own. By METR’s account, it has relatively few tasks that the latest models cannot do (METR, 2026a). Its results page is no longer actively updated, and it rests on self-contained tasks ‘with clear success criteria that can be automatically evaluated’ (METR, 2026b), whereas the health of a codebase can be scored only in part. Agents resolved fewer tasks when they built on code from other agents than on code from people, with drops of up to 13.1%, and many traditional measures of maintainability did not explain the difference (Patel et al., 2026). Automated upkeep can also exceed its brief, since whether a file is stale may depend on what its owner intends. Asked to ‘clean up old branches’, one agent issued a command to delete the branches on the remote server, although the user may have meant only those on their own computer (Hughes, 2026). Capability, moreover, need not turn into use. Narayanan and Kapoor (2025) predict that diffusion will stay slow in high-consequence tasks and that controlling AI will take up a growing share of people’s jobs.

Even if the forecast holds, the case for saved and executed code would stand, since a script can be executed again whether or not anyone can read it. The question of literacy would be only partly settled, because a well-kept codebase can implement a poor analysis. Whether an effect should be allowed to vary across words depends on what a study means to generalise to, and no amount of tidying settles that. Models may come to make such calls well, but someone still has to answer for the result. That is why Nature decided in 2023 to accept no language model as a credited author (“Tools Such as ChatGPT,” 2023).

Answering for a result need not mean reading its code. Few users of lme4 read its source code. They rely instead on its documentation, a published account of its methods (Bates et al., 2015), its tests and the experience of other users. An agent’s analysis might earn trust in a similar way, through independent reanalysis and through tests on simulated data with known answers. A test on one simulated data set would have passed the five scripts above, since their interval contains the population effect of 21.8 ms. Only many such data sets would show how often that interval misses it. Choosing such checks takes statistical knowledge, which may prove the more lasting literacy, although the agents’ choice of interval above suggests that they may come to share it.

The years before any such handover may be the riskiest, and research on automation explains why. Automation leaves its operators to monitor the system and to take over when it fails, while the skills needed for both decay without practice (Bainbridge, 1983). Complacency towards automation arises when other tasks compete for attention, occurs in experts as well as novices and is not overcome by simple practice (Parasuraman & Manzey, 2010). In a meta-analysis of 18 experiments, the more of a task that automation took over, the better performance was while it worked and the worse when it failed (Onnasch et al., 2014).

Studies of AI assistance point to similar risks. Knowledge workers more confident in generative AI reported less critical thinking (Lee et al., 2025). Developers who learned a software package with AI assistance understood it less well and were not significantly faster (Shen & Tamkin, 2026). In the trial of consultants above, those given ChatGPT showed no sign of answering technical questions better without it afterwards and, in an exploratory analysis, became more likely to believe that it could solve problems it could not (Wiles et al., 2026). Messeri and Crockett (2024) warn that AI tools can also leave scientists believing they understand more than they do. The evidence is not uniform, since a meta-analysis of programming education found no reliable effect on exam scores, in either direction, when students could not use the tools in the exam (Maier et al., 2026). As agents improve, they give their supervisors fewer errors to catch, and so less practice at catching the ones that remain.

The uncertainty matters most to early-career researchers, since a doctoral student starting now would finish at about the time of my forecast. I would still advise learning to read and write R or Python. For now, that is the most direct way to check an agent’s work, and understanding seems to come more readily from working through code than from delegating it (Balepur et al., 2026; Shen & Tamkin, 2026). I would be slower to advise memorising syntax, and quicker to advise study design, statistics and the habit of asking how a result could be wrong, which should hold their value however the next few years unfold.

A Workflow for Research With Coding Agents

The experiment points to a workflow built on the three choices reviewed above, the tools, the requests and the record, with checking and upkeep between them. I expect the steps on checking and upkeep to change most over the next few years.

  1. Choose the tools deliberately. The model in this experiment was proprietary, a choice that McLoughlin et al. (2026) suggest might be reasonable when, as here, the model itself is the object of study (see also Palmer et al., 2024). Because the agents’ scripts were saved and executed, a later change to the model would affect only the scripts that it wrote afterwards. Where a language model processes the data itself, as in text annotation, its replies are the results, and a model whose version can be fixed, such as an open model run locally, is the safer choice (Palmer et al., 2024; Spirling, 2023). Real data add a further constraint. An agent sends what it reads to the model, so with a hosted model, the terms of consent and data protection need checking first.

  2. Ask for a script, and specify the analysis. An analysis plan written before any code, ideally in a preregistration, allows every request to be a specified one. A prompt can also ask for the lockfile and tests reviewed above before the code meets real data. One such test would check, over many data sets simulated with pilotr, that the code recovers the known parameters and that its intervals contain them at the stated rate (Morris et al., 2019). Where a decision remains open, it may help to form a view before seeing the agent’s, or to ask it for the best case for each option, two approaches that Herdağdelen et al. (2026) suggest exploring.

  3. Check every change, and execute every script again. Every script run was told to work only inside its own folder, yet 3 of the 24 in the first round wrote files elsewhere. For now, the researcher therefore has to read each change before accepting it and, as was done here, execute each script again in a fresh R process. An integrated development environment such as RStudio or Positron makes both routine, since it shows the lines that each change adds or removes and can start a fresh R process. Reading has its limits, however, since a growing project soon outruns any reader. The checking then has to rest on tests, simulated data and independent reanalysis, and tests alone are not enough. Maintainers of three open-source projects would not have merged roughly half of the patches by agents of 2024 and 2025 that had passed a benchmark’s tests, although those agents had no chance to respond to feedback (Whitfill et al., 2026).

  4. Ask for the upkeep, for as long as it has to be asked for. After each substantial change, ask the agent to update the documentation, remove stale files and resolve inconsistencies and duplicated code, and then check what it did. Asking may not be enough, since repeated guidance did not slow the decline in SlopCodeBench (Orlanski et al., 2026). Separate agents can take on these chores, as in Carlini’s project (Carlini, 2026), but their work needs checking too.

  5. Record everything, the effort level included. The record should follow the reporting guidelines reviewed above (Baltes et al., 2026; Feuerriegel et al., 2026) and include the effort level, which I did not record in the first round. Here, the two runs at xhigh returned the first round’s results, which the same runs had not returned at medium effort. The project is under version control, and each script is saved with its outputs, a record of the environment, the prompts, the agent’s replies and a log of its tool calls.

Used in this way, coding agents can make an AI-assisted analysis far more reproducible than a reply written without running code. Their summaries of their own work, however, are more text generated by the same model, so for now, the checking falls to a researcher who can specify, read and execute the code. How long that will hold is the least certain claim I have made. That someone will have to answer for the result is among the most certain.

Limits

The experiment used one language model and one simulated data set, on which the lower bound of the interval for the priming effect lay close to zero. The data were clean and fully described in the prompt, so the agents faced none of the exclusions, coding errors and gaps in documentation of real data. The two rounds differed in date, in the version of Claude Code and in the system and the versions of R and lme4 that the agents worked with. The first round’s effort level, that of the session that launched it, went unrecorded, so only two runs at xhigh link the differences between the rounds to the effort level, a link they suggest without establishing. With eight runs in each combination of condition and route, the counts describe these runs and do not estimate rates.

The follow-up was designed after the first results on the balanced data. The specified request contained the model formula and the function for the interval, so the agreement among its scripts tested implementation more than analysis. The prose route imitated a chat without a code interpreter, although many chat assistants now have one. An assistant that runs code and lets the researcher keep it could close much of the gap with a coding agent. The prose agents had no time limit and took up to 29 minutes per reply, so the route shows what prose replies can achieve with ample time.

The experiment says little directly about coding literacy. I wrote every request as someone who reads R, so it cannot show what a researcher without R would achieve with the same agents. Each run wrote one short script in one sitting, so the upkeep of a growing project lies outside it. For that, I rely on my own experience and on other studies, several of them from the companies that make these tools. Above all, these results describe one model in autumn 2026, and I would expect some of them to age quickly.
