Generative AI now takes part in most stages of research, from reading the literature to writing and analysing. Each of its replies is a sample. A language model builds a reply by drawing one token at a time from a probability distribution, so the same request can return a different reply (Holtzman et al., 2020). The model behind a product name is also updated over time (Chen et al., 2024). Reproducibility, in the sense set out by the National Academies of Sciences, Engineering, and Medicine (2019), means obtaining consistent results from the same input data, computational steps, methods, code and conditions of analysis. A reply in a chat window meets few of those conditions. Its computations happen out of view, the settings that shaped it are rarely shown and the next reply to the same request may differ.

Agentic tools work differently. Claude Code reads a project, edits its files and runs commands in the researcher’s own environment (Anthropic, n.d.-b). ChatGPT Work acts across a user’s apps and files and turns a goal into finished documents, spreadsheets and web apps (OpenAI, 2026). When such a tool writes an R or Python script, the variability of the model enters while the script is being written. Once the script is saved, the analysis is as deterministic as any other code. It can be read, tested, kept under version control and executed again.

This post examines that division of labour with an experiment that I ran from a Claude Code session. The session gave one analysis request, about a simulated semantic-priming data set, to 48 Claude Code agents. Half of them answered in prose, as a chat assistant without a code interpreter would, and half wrote an R script that was then executed. The data come from my pilotr package (Bernabeu, 2026b), which generates identical data from a design specification in R and in Python. The results bear on two questions: what executing code adds to an AI-assisted analysis, and what the researcher needs to know of R and of an integrated development environment (IDE) to make use of it.

Development

This section reviews the sources of variation in the output of language models and the case for moving computation into code. It then describes the data and the design of the experiment.

Where the Variation Comes From

Setting the sampling temperature to zero, which should select the most probable token at every step, does not make hosted models deterministic. When Ouyang et al. (2025) asked ChatGPT at its default temperature to write code for 829 programming problems, the code returned by repeated requests never produced the same test output for between 47.56% and 75.76% of the problems, depending on the benchmark. A temperature of zero reduced that variation without removing it. Atıl et al. (2025) ran five hosted models 10 times on each of eight tasks with settings meant to be deterministic and found that accuracy varied by up to 15% across runs. He and Thinking Machines Lab (2025) traced much of this behaviour to the way inference servers work. The number of requests processed together changes with the load on the server, and kernels whose floating-point arithmetic depends on that number change the result. In their test with an open model, 1,000 completions of one prompt at temperature zero contained 80 distinct texts, and kernels made invariant to the batch size brought them down to one. Anthropic’s documentation states that results will not be fully deterministic even at temperature zero (Anthropic, n.d.-a), and its most recent models reject any temperature other than the default (Anthropic, n.d.-c), so their users cannot lower it at all.

Sampling is one source of variation among several. Chen et al. (2024) compared the March and June 2023 versions of the two models behind ChatGPT on the same tasks and found substantial changes in behaviour within three months. One of them identified prime numbers with 84% accuracy in March and 51% in June. The format of a prompt matters too. Changes in prompt formatting that preserve meaning altered the accuracy of one open model by up to 76 percentage points in few-shot tasks (Sclar et al., 2024). When models annotated text for hypothesis tests, the choice of model and prompting strategy led to incorrect conclusions for about one in three hypotheses with state-of-the-art models (Baumann et al., 2025). The providers of closed models can also change them at any time (Spirling, 2023), which is one reason why Palmer et al. (2024) argue that research using them needs explicit justification. In a chat interface, none of these sources is under the user’s control, and few are recorded.

Moving the Computation Into Code

The practices of reproducible computational research ask that every result be traceable to the steps that produced it and that manual data manipulation be avoided. They also ask that scripts be kept under version control, that the versions of external programs be archived and that random seeds be recorded (Sandve et al., 2013; see also Peng, 2011; Wilson et al., 2017). A script written by an agent into a project under version control is such a record. The variability of the model does not disappear, since a second request would yield a different script, but it is confined to the writing of the script, where the researcher can inspect it. The software environment still has to be kept. When Trisovic et al. (2022) re-executed R files deposited with published research data, 74% failed to complete without error, and 56% still failed after automatic code cleaning. A lockfile from renv (Ushey & Wickham, 2026) and a record of the R session reduce that risk.

The data set used in the experiment illustrates the same principle on a small scale. pilotr stores a design as a portable specification and draws its random numbers from its own generator, so the same specification and seed produce the same data in R and in Python (Bernabeu, 2026b). The specification describes 30 participants who each respond to 24 words, once after a related prime and once after an unrelated one. Reaction times follow a shifted lognormal distribution, with by-participant and by-item random intercepts and priming slopes and a word-frequency covariate.

The three checksums are identical, so the data set can be rebuilt byte for byte in either language from a few lines of JavaScript Object Notation (JSON). Because the data are simulated, the population they come from is also known. For a shifted lognormal response, the mean reaction time in each condition follows from the parameters of the specification, which gives the size of the priming effect in the population. The same parameters determine how much the effect varies from one participant, or one word, to the next, which the code below estimates by drawing a million participants and a million words.

fixed <- spec$fixed; random <- spec$random; frequency <- spec$predictors[[1]]
mu <- fixed$intercept + fixed$coefficients$frequency * frequency$mean

# The variance, at a given prime code, of the terms that belong to one unit
# (participant or item): its random intercept and slope and their covariance.
unit_variance <- function(unit, prime_code) {
  unit$intercept_sd^2 + prime_code^2 * unit$slopes$prime_c^2 + 2 * prime_code *
    unit$intercept_sd * unit$slopes$prime_c * unit$correlations[['intercept,prime_c']]
}
residual_variance <- (fixed$coefficients$frequency * frequency$sd)^2 + spec$response$sigma^2

# The mean of a lognormal variable is exp(mu + variance / 2), and the shift
# cancels out of the difference between conditions.
population_mean <- function(prime_code) {
  spec$response$shift + exp(mu + fixed$coefficients$prime_c * prime_code +
    (unit_variance(random$subject, prime_code) + unit_variance(random$item, prime_code) +
       residual_variance) / 2)
}
population_effect <- population_mean(0.5) - population_mean(-0.5)

# The priming effect of one participant (or word), averaged over the other
# unit and the residual, for a million simulated participants (or words)
effect_sd <- function(unit, other) {
  z <- matrix(rnorm(2e6), ncol = 2)
  rho <- unit$correlations[['intercept,prime_c']]
  intercept <- unit$intercept_sd * z[, 1]
  slope <- unit$slopes$prime_c * (rho * z[, 1] + sqrt(1 - rho^2) * z[, 2])
  unit_mean <- function(prime_code) exp(mu + intercept + prime_code * (fixed$coefficients$prime_c + slope) +
    (unit_variance(other, prime_code) + residual_variance) / 2)
  sd(unit_mean(0.5) - unit_mean(-0.5))
}
set.seed(2026)
effect_sds <- c(participants = effect_sd(random$subject, random$item),
                words = effect_sd(random$item, random$subject))
sample_effect <- with(regenerated, mean(rt[prime == 'unrelated']) - mean(rt[prime == 'related']))

c(population_effect = population_effect, sample_effect = sample_effect,
  sd_across_participants = effect_sds[['participants']], sd_across_words = effect_sds[['words']])

Every run received the same description of the data and the same question: ‘How large is the priming effect, that is, how much slower are responses after unrelated primes than after related primes? Give the estimate in milliseconds with a 95% confidence interval.’ The runs differed in three respects. The request was either open, leaving the analysis to the agent, or specified, naming the model, the coding of the predictor and the function that computes the interval. The route was either prose or a script. In the prose route, the agent could read the data file but was told to run no code and to answer in its reply, as it would in a chat without a code interpreter. In the script route, the agent wrote an R script and could run it to check its work. Every run had to end with a line in a fixed format giving the estimate and the interval, so that the answers could be compared by code. Most runs analysed the balanced data set described above. A follow-up gave the specified request with an unbalanced version of the data, described in the Results, together with one added sentence saying that incorrect responses had been removed.

The design has eight runs in each combination of condition and route, 48 in total, all run on 29 September 2026 with Claude Code 2.1.284. The 32 runs on the balanced data were launched eight at a time, in a random order across conditions. I designed the follow-up with unbalanced data after seeing the first results, and its 16 runs were launched afterwards, also in a random order. Each run was a separate agent, started by the session in the background with the session’s model and reasoning settings, and given its own directory holding only the data file. The logs of their tool calls show that every prose run used no tool other than reading its data file. Of the 24 script runs, 21 touched no file outside their own directory. The other three wrote exploratory R files to the session’s scratch folder, which Claude Code designates for temporary files, under shared names such as explore.R. Each wrote and ran such a file within a single command and read only its own data, so none of them appears to have run another’s code, although they were not fully isolated. The first eight agents also started in the experiment’s own folder, which holds the specification, and their logs show no access to it. The session then executed each final script three times, each time in a fresh R process and a fresh copy of its directory, and this page executes every script once more when it is built.

Results

The results cover the agreement between runs, the accuracy of the prose replies, the follow-up with unbalanced data, the re-execution of the scripts and the time each route took.

The open request left every analytic decision to the agents, and the eight scripts converged on one analysis. Each fitted a linear mixed-effects model to the untransformed reaction times, with crossed random effects for participants and words. Each found that the maximal model was singular, because in this sample the priming effect appeared to vary little across participants, so that the estimated by-participant slope was perfectly correlated with the intercept, and dropped that slope. All eight then computed the interval from a t distribution with Satterthwaite degrees of freedom. Four of them also included word frequency as a covariate, which cannot change the estimate in a balanced design, since every word appears in both conditions. The prose replies reached the same interval by another path. They decomposed the 720 paired differences into participant, item and residual components, and in a balanced design that decomposition gives the same standard error as the reduced model. Some of these replies equated their decomposition with the maximal model, although the scripts’ fit of that model gives a slightly wider interval. With the specified request, both routes returned the Wald interval of the maximal model.

The simplification the agents chose is the parsimonious strategy that Matuschek et al. (2017) defend on the grounds of power, and it sits uneasily with the maximal structure that Barr et al. (2013) recommend. Here the population is known, and it shows what the choice rested on. In this sample, the effect appeared to vary little across participants and a great deal across words, whereas in the population it varies more across participants than across words. The agents followed the sample, as any analyst of real data would have to.

Of the 16 agents given the open request, 14 mentioned in their replies the narrower interval of a by-participant analysis. A paired t test over the participants’ mean differences gives an interval of [5.58, 31.46] ms, which excludes zero, whereas the same test over the words’ mean differences reproduces the interval of the open-request scripts, [−1.53, 38.57] ms. The agents set the by-participant analysis aside because it ignores how the effect varies across words, which overstates the evidence for generalising beyond the words sampled. In this simulation the effect is real, so the by-participant test reached the right conclusion by an analysis too liberal for the purpose, and the mixed models, whose intervals include zero, missed it. The data set was small, and the conclusion sat on a boundary that the choice of analysis could move.

The agents need not have agreed so closely with one another. When 29 teams analysed one data set to answer one question, their odds ratios ranged from 0.89 to 2.93, and 20 of the 29 teams found a statistically significant effect (Silberzahn et al., 2018). When 70 teams tested the same hypotheses on one neuroimaging data set, no two of them chose the same workflow (Botvinik-Nezer et al., 2020). Coding agents can show the same diversity. Autonomous AI analysts given one data set and one hypothesis reached divergent verdicts in three domains, and their conclusions shifted with the model and the prompt (Bertran et al., 2026). Alizadeh et al. (2026) ran Claude Code and Codex 20 times each on a many-analysts study of immigration and social policy. The agents varied their model specifications at least as much as the human teams had, and their estimates stayed broadly in line with the human consensus. The authors located the agents’ vulnerability in the interpretation of estimates, and less in the estimates themselves. The task in this post was far simpler, with two conditions, a balanced design and one obvious family of models, and one model in one session made the same choices eight times out of eight. A different model, version or wording could choose differently, and the interval would move with the choice.

When the Design Is Unbalanced

The follow-up removed 86 of the 1,440 trials at random, as if they had been errors, which leaves some participant-word pairs with one condition or none. Without balance, the estimate of the mixed model no longer equals the difference between the condition means, which is 21.43 ms, and the REML fit has to be found numerically. The eight scripts printed the same result, an estimate of 21.79 ms with an interval of [0.58, 43.00] ms. Removing these trials moved the lower bound of the specified model’s interval from −0.74 to 0.58 ms, and with it the conclusion.

The prose replies approximated the model with weighted averages of the per-word effects and estimates of the variance components from the observed mean squares. Table 3 sets their results beside the executed one.

Time Taken

Figure 2 shows how long each run took, from the request to the final reply. With the specified request, a script took a median of 0.7 minutes, whereas a prose reply took 13.7 minutes on the balanced data and 14.6 on the unbalanced data. The difference is the work of computing by hand what R computes in a fraction of a second, and it is far more deliberation than a reply in a chat window usually receives. The open request took the scripts longer than the specified one, because the agents compared several random-effects structures and ran checks of their own. The runs shared one service and overlapped in time, and the follow-up ran later than the main runs, so the durations include some waiting and are best read as orders of magnitude.

Discussion

The discussion considers what executing code contributed and what the researcher contributes, and outlines a workflow that follows from the results before turning to the limits of the experiment.

What Executing Code Contributed

No text in this experiment was repeated, and every executed script gave the same output each time it ran. That second fact follows from executing saved code in a fixed environment. The agreement between runs is a separate matter. On balanced data, the prose replies were as consistent as the scripts, so the consistency came from the model and from how precisely the request specified the analysis. What the executed scripts added was exactness and a record that can be checked. On unbalanced data, where the model has to be fitted numerically, every script returned the exact result, whereas each prose reply returned an approximation. Even where the prose replies were exact, only code could show it. Without recomputing their quantities in R, a correct reply could not be told apart from a confident error.

The results also qualify the studies reviewed above. Those found large variation from one request to the next in code generation and in benchmark accuracy (Atıl et al., 2025; Ouyang et al., 2025). Here, on balanced data, the agents converged on the same analysis and the same numbers, and the variation lay in the wording and in secondary choices such as a covariate that could not affect the estimate. On unbalanced data, the scripts still converged, whereas the prose replies did not. Bertran et al. (2026) propose deploying AI analysts against a published specification to reveal how much disagreement comes from underspecified design choices. In this experiment, the open request produced little disagreement to reveal, and the specification mattered mainly because it fixed which interval was computed. The consistency observed belongs to one model on one structured task on one day, and the reproducibility of a study cannot rest on it. A script can be checked, whereas the consistency of a model can only be observed, and it may not survive the next update (Chen et al., 2024).

Why Direct Experience With R and an IDE Matters

The specified request is where the researcher’s knowledge entered the experiment. Writing it required knowing that the data call for crossed random effects and that the random slopes included change the interval (Barr et al., 2013). It also required knowing that transforming reaction times can change the effects being tested (Lo & Andrews, 2015) and that a singular fit is an estimate on the boundary of the parameter space. Given that request, every script returned the same result in under a minute. The request also shows the limits of a specification. It fixed a Wald interval, which treats the t statistic as normal and is anticonservative with few items (Luke, 2017). I chose it because one function call defines it exactly and so makes the scripts comparable. An analysis for publication would do better to request Satterthwaite or Kenward–Roger degrees of freedom, as the agents did of their own accord under the open request. A specification is only as good as the knowledge of the person who writes it, and an agent will implement a weak one faithfully.

Reading the code is the second point of entry. The scripts in this experiment ran from 30 to 143 lines. A researcher who reads R can confirm in a few minutes that a script fits the intended model to the intended rows, and can spot a dropped random slope, a silent exclusion of trials or an unplanned transformation. The same researcher can also judge whether such a choice is defensible, as with the by-participant slope that these agents dropped. An IDE makes those checks routine, with diffs of every change, version control, a view of the objects in memory and the option of running a script again in a fresh session. Without that experience, the researcher is left with the agent’s summary of its own work, which is another text generated by the same model.

Research on automation explains why this knowledge needs maintaining. Bainbridge (1983) observed that automation leaves its operators to monitor the system and to take over when it fails, while the skills needed for both deteriorate when they are no longer practised. Complacency towards automation arises when other tasks compete for attention, occurs in experts as well as novices and is not overcome by simple practice (Parasuraman & Manzey, 2010). People’s impressions of AI assistance can also be wrong. In a randomised trial with 16 experienced open-source developers, allowing AI tools increased the time taken to complete tasks by 19%, although the developers believed afterwards that it had reduced it by 20% (Becker et al., 2025). In a survey of 319 knowledge workers, higher confidence in generative AI was associated with less self-reported critical thinking, and higher confidence in oneself with more (Lee et al., 2025). When software engineers learned a new programming library with or without AI assistance, those who used it scored lower on a subsequent test of their understanding of the library, with no significant gain in speed (Shen & Tamkin, 2026). Messeri and Crockett (2024) warn that AI tools can leave scientists believing that they understand more than they do. For early-career researchers in particular, the ability to check an agent’s code has to be built by writing code, and this workflow depends on it.

A Reproducible Workflow With Coding Agents

The experiment suggests a workflow in which the project lives under version control, with a lockfile for its packages. The analysis plan is written before the agent writes any code, ideally in a preregistration, so that the request is a specified one. The agent writes scripts into files, and the researcher reads each diff before accepting it, runs the scripts in a fresh session and commits them together with their outputs and a record of the environment. The prompts, the agent’s replies and a log of its tool calls are kept beside the scripts, as they are for this post. Where possible, the agent’s code is first tested on simulated data with known parameters, as pilotr allows, so that its ability to recover an effect is checked before it meets real data. Finally, some uses of a model process data directly, as in text annotation. There, a model whose version can be pinned, such as an open model run locally, is preferable to one that can change without notice (Palmer et al., 2024; Spirling, 2023).

Limitations

The experiment used one model, one version of Claude Code and one day, with one simulated data set whose interval sat close to zero. The agents ran concurrently as background agents of a single session, and interactive use of the same tool may differ. Their model is not named here, and its reasoning was not retained in the transcripts, so the hand calculations are known only from the replies. As described above, three script runs used a shared scratch folder and the first eight runs started in the folder that holds the specification. The follow-up was designed after the first results and run later than the main runs. The specified request contained the model formula and the function for the interval, so the agreement among its scripts tested implementation more than analysis. The prose route imitated a chat without a code interpreter, but its replies drew on far longer deliberation than a chat usually gives. Commercial chat assistants often run code in a sandbox, which narrows the contrast, although the code and its environment are seldom kept with the result. The analytic choices of the open-request scripts were coded by the same session that ran the experiment, and they can be checked against the scripts in the repository. Finally, with eight runs in each cell, the counts describe these runs and do not estimate rates.
