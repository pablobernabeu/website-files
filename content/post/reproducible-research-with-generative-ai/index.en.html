Generative artificial intelligence (AI) is now used at many stages of research, from reading the literature to writing and analysing. Each of its replies is a sample, drawn one token at a time from a probability distribution, so the same request can return a different reply (Holtzman et al., 2020). Reproducibility, in the sense set out by the National Academies of Sciences, Engineering, and Medicine (2019, p. 46), means obtaining consistent results from the same input data, computational steps, methods, code and conditions of analysis. A reply in a chat window meets few of those conditions, since its computations happen out of view and the settings that shaped it are rarely shown.

Agentic tools such as Claude Code can instead read a project, edit its files and run commands, on the researcher’s own computer or in a cloud session (Anthropic, n.d.-b). OpenAI (2026) describes ChatGPT Work as acting across a user’s apps and files to turn a goal into finished documents, spreadsheets and web apps. When such a tool writes an R or Python script, the model’s variability enters while the script is written. Once saved, the script is as deterministic as any other code, and it can be read, tested, kept under version control and executed again.

This post examines that division of labour with an experiment. A Claude Code session put one analysis question, about a semantic-priming data set simulated with my pilotr package (Bernabeu, 2026b), to 48 Claude Code agents. Half of them answered in prose, as a chat assistant without a code interpreter would, and half wrote an R script that was then executed. The results bear on two questions: what executing code adds to an AI-assisted analysis and what the researcher needs to know of R to specify, read and check the code that an agent writes.

Development

This section reviews the sources of variation in the output of language models and the case for moving computation into code, and then describes the data and the design of the experiment.

Where the Variation Comes From

Setting the sampling temperature to zero, which should select the most probable token at every step, does not make hosted models deterministic. When Ouyang et al. (2025) asked ChatGPT at its default temperature to write code for 829 programming problems, repeated requests never returned code with the same test output for 47.56% to 75.76% of the problems, depending on the benchmark. A temperature of zero reduced that variation without removing it. Atıl et al. (2025) ran five hosted models 10 times on each of eight tasks with settings meant to be deterministic, and accuracy varied by up to 15 percentage points across runs. He and Thinking Machines Lab (2025) traced much of this behaviour to inference servers, where the number of requests processed together varies with load and changes the result of any kernel whose floating-point arithmetic depends on it. In their test with an open model, 1,000 completions of one prompt at temperature zero contained 80 distinct texts, and kernels made invariant to the batch size brought them down to one. Anthropic (n.d.-a) states that results will not be fully deterministic even at temperature zero, and its most recent models accept only the default temperature (Anthropic, n.d.-c).

Sampling is one source of variation among several. Chen et al. (2024) found substantial changes in behaviour between the March and June 2023 versions of the two models behind ChatGPT, one of which classified numbers as prime or composite with 84% accuracy in March and 51% in June. Meaning-preserving changes in the format of a prompt altered the accuracy of one open model by up to 76 percentage points in few-shot tasks (Sclar et al., 2024). When models annotated text for hypothesis tests, the choice of model and prompting strategy led to incorrect conclusions for about one in three hypotheses with state-of-the-art models (Baumann et al., 2025). Providers can also change closed models at any time (Spirling, 2023), which is one reason Palmer et al. (2024) argue that research using them needs explicit justification. In a chat interface, none of these sources is under the user’s control, and few are recorded.

Moving the Computation Into Code

Reproducible computational research asks that every result be traceable to the steps that produced it, without manual data manipulation. Scripts should be kept under version control, the versions of external programs archived and random seeds recorded (Sandve et al., 2013; see also Peng, 2011; Wilson et al., 2017). A script that an agent writes into a project under version control documents the steps behind a result, but the software environment has to be recorded as well. When Trisovic et al. (2022) re-executed R files deposited with published research data, allowing each a fixed time, 75% of those that finished within it stopped with an error, and 60% still did after automatic code cleaning. A lockfile from renv (Ushey & Wickham, 2026) and a record of the R session reduce that risk and show what has changed when a script behaves differently elsewhere.

The Simulated Data

The data set used in the experiment was simulated with pilotr, which generates data in R and in Python from a portable design specification. Because pilotr draws its random numbers from its own generator, and the specification used here rounds the reaction times to whole milliseconds, the same specification and seed produce identical data in both languages (Bernabeu, 2026b). The specification describes 30 participants who each respond to 24 words, once after a related prime and once after an unrelated one. Reaction times follow a shifted lognormal distribution, with a word-frequency covariate and with by-participant and by-item random intercepts and priming slopes.

Because the data are simulated, their population is known. For a shifted lognormal response, the parameters of the specification give the mean reaction time after each type of prime, and so the population priming effect. They also determine how much the effect varies across participants and across words, which the code below estimates by drawing a million of each.

fixed <- spec$fixed; random <- spec$random; frequency <- spec$predictors[[1]]
mu <- fixed$intercept + fixed$coefficients$frequency * frequency$mean

# The variance, at a given prime code, of the terms that belong to one unit
# (participant or item): its random intercept and slope and their covariance.
unit_variance <- function(unit, prime_code) {
  unit$intercept_sd^2 + prime_code^2 * unit$slopes$prime_c^2 + 2 * prime_code *
    unit$intercept_sd * unit$slopes$prime_c * unit$correlations[['intercept,prime_c']]
}
residual_variance <- (fixed$coefficients$frequency * frequency$sd)^2 + spec$response$sigma^2

# The mean of a lognormal variable is exp(mu + variance / 2), and the shift
# cancels out of the difference between the two types of prime.
population_mean <- function(prime_code) {
  spec$response$shift + exp(mu + fixed$coefficients$prime_c * prime_code +
    (unit_variance(random$subject, prime_code) + unit_variance(random$item, prime_code) +
       residual_variance) / 2)
}
population_effect <- population_mean(0.5) - population_mean(-0.5)

# The priming effect of one participant (or word), averaged over the other
# unit and the residual, for a million simulated participants (or words). A
# word's frequency belongs to the word, so for words it moves with the word's
# intercept and is not averaged out.
effect_sd <- function(unit, other, word = FALSE) {
  z <- matrix(rnorm(2e6), ncol = 2)
  rho <- unit$correlations[['intercept,prime_c']]
  intercept <- unit$intercept_sd * z[, 1]
  slope <- unit$slopes$prime_c * (rho * z[, 1] + sqrt(1 - rho^2) * z[, 2])
  averaged <- residual_variance
  if (word) {
    intercept <- intercept + fixed$coefficients$frequency * frequency$sd * rnorm(nrow(z))
    averaged <- spec$response$sigma^2
  }
  unit_mean <- function(prime_code) exp(mu + intercept + prime_code * (fixed$coefficients$prime_c + slope) +
    (unit_variance(other, prime_code) + averaged) / 2)
  sd(unit_mean(0.5) - unit_mean(-0.5))
}

Every run received a description of the data and the same question: ‘How large is the priming effect, that is, how much slower are responses after unrelated primes than after related primes? Give the estimate in milliseconds with a 95% confidence interval.’ Every run also had to end with a line giving the estimate and the interval in a fixed format, so that the answers could be compared by code. The request was either open, leaving the analysis to the agent, or specified, naming the model, the coding of the predictor and the function that computes the interval. The route was either prose or a script. In the prose route, the agent could read the data file but was told to run no code, to answer in its reply as it would in a chat without a code interpreter and, if it could not compute the answer exactly, to give its best estimate. In the script route, the agent wrote an R script and could run it to check its work, and the instructions named lme4 (Bates et al., 2015), lmerTest (Kuznetsova et al., 2017), emmeans and dplyr among the installed packages. The data were either the balanced data set described above or, in a follow-up with the specified request, an unbalanced version from which 86 of the 1,440 trials had been removed at random, and one sentence added to the request said that incorrect responses had been removed. The three combinations of data and request are the conditions of the experiment.

The prompts are stored with this post, together with the data, the scripts, each run’s final reply and a log of its tool calls, but not the agents’ full transcripts. The design has eight runs in each combination of condition and route, 48 in total, all run on 29 September 2026 with Claude Code 2.1.284 and the model Claude Opus 5.5 (claude-opus-5-5). The 32 runs on the balanced data were launched eight at a time, in a random order across conditions. I designed the follow-up with unbalanced data after seeing the first results, and its 16 runs were launched afterwards, also in a random order.

Each run was a separate agent with the session’s model and reasoning settings, started in the background and pointed to a directory of its own that held only the data file. The logs of their tool calls record when each run started and ended, and show that each prose run used tools only to read its data file and that 21 of the 24 script runs touched no file outside their own directory. The other three wrote exploratory R files under shared names such as explore.R to the session’s scratch folder, but each wrote and ran such a file within a single command and read only its own data, so none appears to have run another’s code. One of them also read, from the session’s task folder, the output of an R command that ran in the background. The first eight agents were launched from the experiment’s own folder, which holds the pilotr specification, and their logs show no access to it.

The session then executed each final script three times, each time in a fresh R process and a fresh copy of its directory, and recorded the versions of R, lme4, lmerTest and Matrix.

# deviations, built with the hidden checks earlier on the page, holds each of

# Runs whose differences are equal share one mark, with their count above it.
# Of two marks too close to tell apart, the one standing for fewer runs is
# lowered a little.
lowered <- function(deviation, runs) {
  lower <- rep(FALSE, length(deviation))
  for (i in seq_along(deviation)[-1]) {
    if (deviation[i] - deviation[i - 1] < 0.05) {
      lower[if (runs[i] <= runs[i - 1]) i else i - 1] <- TRUE
    }
  }
  lower
}

Given the open request, the eight scripts converged on one analysis. Each fitted a linear mixed-effects model to the untransformed reaction times, with crossed random effects for participants and words. The maximal model was singular, with the estimated by-participant slope perfectly correlated with the intercept, and every script dropped that slope. All eight then computed the interval from a t distribution with Satterthwaite degrees of freedom, which the lmerTest package adds to models fitted with lme4 (Kuznetsova et al., 2017). Four of them also included word frequency as a covariate, although in a balanced design it cannot change the estimate, since every word appears after both types of prime.

The simplification the agents chose is the parsimonious strategy that Matuschek et al. (2017) defend on the grounds of power, and it sits uneasily with the maximal structure that Barr et al. (2013) recommend. The known population shows what the choice rested on. Fitted to this sample, the maximal model puts the standard deviation of the priming effect at 8.9 ms across participants and 29.8 ms across words. In the population, the two are 18.3 and 12.9 ms. The agents followed the sample, as any analyst of real data would have to.

The prose replies to the open request reached the same interval as the scripts by decomposing the 720 paired differences into participant, item and residual components. In a balanced design, this decomposition gives the same standard error as the scripts’ model without by-participant slopes. Five of these replies equated their decomposition with the maximal model, although that model keeps a small by-participant slope, perfectly correlated with the intercept, and gives a slightly wider Satterthwaite interval, [−1.78, 38.82] ms. With the specified request, both routes returned the Wald interval of the maximal model, which is narrower than either Satterthwaite interval because it takes its critical value from the normal distribution.

Every prose reply to the open request, and six of the eight summaries that accompanied its scripts, mentioned the narrower interval of a by-participant analysis. A paired t test over the participants’ mean differences gives [5.58, 31.46] ms, which excludes zero, and the same test over the words’ mean differences reproduces the interval of the open-request scripts, [−1.53, 38.57] ms. Each of those replies and summaries set the by-participant analysis aside because it ignores how the effect varies across words and so overstates the evidence for generalising beyond the words sampled. Since the effect is real in this simulation, the by-participant test reached the right conclusion by an analysis too liberal for the purpose. A test of the mixed models at the .05 level would have missed the effect, although their intervals contain its population value of 21.8 ms.

When the Design Is Unbalanced

In the unbalanced data, 84 participant-word pairs are left with a trial after only one type of prime and 1 with no trial at all. Without balance, the estimate of the mixed model, 21.79 ms in all eight scripts, no longer equals the difference between the mean reaction times after the two types of prime, 21.43 ms. Nor does the REML fit reduce to mean squares and cross-products, so it has to be found numerically. Removing the trials moved the lower bound of the Wald interval that the specified request fixed from −0.74 to 0.58 ms, so that it no longer included zero. With Satterthwaite degrees of freedom, which the open-request scripts used, the same model gives [−0.57, 44.15] ms, which still includes zero.

The prose replies approximated the model with weighted averages of the per-word effects and estimates of the variance components from the observed mean squares. Unlike the replies to the specified request on the balanced data, each of them put the variance of the by-participant slopes at or near zero. The fit that lme4 found kept a by-participant slope with a standard deviation of 6.7 ms, perfectly correlated with the intercepts. The replies’ results therefore lie closer to those of the model without by-participant slopes, 21.85 [0.77, 42.92] ms, than to the executed result. Discussion

The first two parts of the discussion take up the two questions of the introduction, and the last two outline a workflow and the limits of the experiment.

What Executing Code Contributed

No text in this experiment was repeated, yet every executed script printed the same output each time the session ran it, as saved code in a fixed environment should. Because the versions of R, lme4, lmerTest and Matrix were recorded and can still be installed, a rebuild of that environment on another machine, with the other packages taken from Ubuntu 24.04, printed the same output. Under newer versions, the only change, in formatting, disappeared when the recorded version of lme4 was restored.

The agreement between runs is a separate matter. On balanced data, the prose replies were as consistent as the scripts, and the open request was answered as consistently as the specified one, so the consistency came from the model and the task. The specified request decided which interval the runs agreed on. The executed scripts added exactness and a record that can be checked. On unbalanced data, where the model has to be fitted numerically, every script returned the exact result and each prose reply an approximation. Even where the prose replies matched the scripts, only recomputing their quantities in R could tell a correct reply from a confident error.

The results also qualify the studies reviewed above, which found large variation from one request to the next in code generation and in benchmark accuracy (Atıl et al., 2025; Ouyang et al., 2025). Many-analysts studies find wide variation among human analysts too. When 29 teams analysed one data set to answer one question, their odds ratios ranged from 0.89 to 2.93, and 20 of the 29 teams found a statistically significant effect (Silberzahn et al., 2018). When 70 teams tested the same hypotheses on one neuroimaging data set, no two chose the same workflow (Botvinik-Nezer et al., 2020). Coding agents can show the same diversity. Autonomous AI analysts given one data set and one hypothesis reached divergent verdicts in three domains, and their conclusions shifted with the model and the prompt (Bertran et al., 2026). Alizadeh et al. (2026) ran Claude Code and Codex 20 times each on a many-analysts study of immigration and social policy. The agents varied their model specifications at least as much as the human teams had, but their estimates stayed broadly in line with the human consensus, and the authors located the agents’ vulnerability in interpretation more than in estimation.

The task in this experiment was far simpler, with two types of prime, participants crossed with words and one obvious family of models. On balanced data, the agents varied only in wording and in secondary choices such as a covariate that could not affect the estimate. On unbalanced data, even the seven different results of the prose replies lay within 0.3 ms of one another. Bertran et al. (2026) propose deploying AI analysts against a published specification to reveal how much disagreement comes from underspecified design choices. Here, the open request produced little disagreement to reveal. That consistency belongs to one model on one structured task and may not survive the next update (Chen et al., 2024). The reproducibility of a study cannot rest on it, whereas a script and the record of its environment can be checked.

Why Direct Experience With R and an IDE Matters

The specified request is where the researcher’s knowledge entered the experiment. Writing it required knowing that the data call for crossed random effects, that the choice of random slopes changes the interval (Barr et al., 2013) and that transforming reaction times can change the effects being tested (Lo & Andrews, 2015). It also required knowing R, since the request names the function that fits the model, writes the model in the formula notation of lme4 and gives the call to confint() that computes the interval. Interpreting the output required knowing that a singular fit is an estimate on the boundary of the parameter space.

The request also shows the limits of a specification. It fixed a Wald interval, which treats the t statistic as normal and is anticonservative with few participants or items (Luke, 2017). I chose it because one function call defines it exactly and so makes the scripts comparable. On the unbalanced data, that choice decided whether the interval excluded zero. An analysis for publication would do better to request Satterthwaite or Kenward–Roger degrees of freedom, as computed in the open-request scripts. None of the 32 runs given the specified request mentioned either.

Reading the code is the second point of entry. The scripts in this experiment were between 30 and 143 lines long. A researcher who reads R can confirm in a few minutes that a script fits the intended model to the intended rows. Such a reader can also spot a dropped random slope, a silent exclusion of trials or an unplanned transformation, and judge whether each is defensible. Every summary of an open-request script reported dropping the by-participant slope and justified it by the fit of the maximal model. Weighing that justification against the chance that the effect varies across participants in the population, as it does in this simulation, takes knowledge that the summary does not supply. Without experience of R, the researcher is left with the agent’s summary of its own work, which is another text generated by the same model.

Research on automation explains why the knowledge needed to specify and read an agent’s code has to be maintained. Bainbridge (1983) observed that automation leaves its operators to monitor the system and to take over when it fails, while the skills needed for both decay without practice. Complacency towards automation arises when other tasks compete for attention, occurs in experts as well as novices and is not overcome by simple practice (Parasuraman & Manzey, 2010). Impressions of AI assistance can also be wrong. In a randomised trial, 16 experienced open-source developers took 19% longer to complete tasks when allowed AI tools, although they believed afterwards that the tools had cut their time by 20% (Becker et al., 2025). Among 319 knowledge workers surveyed, higher confidence in generative AI was associated with less self-reported critical thinking, and higher self-confidence with more (Lee et al., 2025). Developers who learned a new programming library with AI assistance scored lower on a later test of their understanding of it than those who learned without, and were not significantly faster (Shen & Tamkin, 2026). Messeri and Crockett (2024) warn that AI tools can leave scientists believing that they understand more than they do. For early-career researchers in particular, the ability to check an agent’s code has to be built by writing code, and the workflow outlined below depends on that ability.

The checks this experiment needed, from reading each script to comparing its outputs line by line, are what an integrated development environment (IDE) makes routine. An IDE shows a diff of every change, works with version control, displays the objects in memory and can run a script again in a fresh session, which makes it a practical place to work with an agent’s code.

A Reproducible Workflow With Coding Agents

The experiment suggests a workflow in which the project lives under version control, with a lockfile for its packages. The analysis plan is written before the agent writes any code, ideally in a preregistration, so that the request is a specified one. The agent writes scripts into files, and the researcher reads each diff before accepting it, runs the scripts in a fresh session and commits them together with their outputs and a record of the environment. The prompts, the agent’s replies and a log of its tool calls are kept beside the scripts. Where possible, the agent’s code is first tested on simulated data with known parameters, as pilotr allows, to check that it recovers the effect before it meets real data. Where a model processes the data itself, as in text annotation, it is better to use one whose version can be pinned, such as an open model run locally (Palmer et al., 2024; Spirling, 2023).

Limitations

The experiment ran on one day, with one model, one version of Claude Code and one simulated data set, on which the lower bound of the interval for the priming effect lay close to zero. With eight runs in each combination of condition and route, the counts describe these runs and do not estimate rates. The follow-up was designed after the first results. The specified request contained the model formula and the function for the interval, so the agreement among its scripts tested implementation more than analysis. The prose route imitated a chat without a code interpreter, although many chat assistants can now run code. Its agents had no time limit and took up to 29 minutes per reply.
