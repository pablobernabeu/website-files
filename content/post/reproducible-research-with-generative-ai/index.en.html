Generative artificial intelligence (AI) is now used at many stages of research. A language model writes each reply one token (often a word or part of one) at a time, sampling from a probability distribution, so the same request can return a different reply (Holtzman et al., 2020). Reproducibility means obtaining consistent results from the same input data, computational steps, methods, code and conditions of analysis (National Academies of Sciences, Engineering, and Medicine, 2019, p. 46). A reply in a chat window meets few of those conditions, since its computations happen out of view and the settings behind it are rarely shown.

Agentic tools such as Claude Code can instead read a project, edit its files and run commands (Anthropic, n.d.-c). When such a tool writes an R or Python script, the model’s variability enters while the script is written. Once saved, the script gives the same output for the same input in the same software environment. It can be read, tested, executed again and kept under version control, in a system such as Git that records each version of a project’s files.

I examined that division of labour in an experiment. In each of two rounds, one Claude Code session (a single conversation with the tool) put an analysis question to 48 agents, each a separate run of the language model working alone with Claude Code’s tools. The question concerned a semantic-priming data set simulated with my pilotr package (Bernabeu, 2026b). Half of the agents answered in prose, as a chat assistant without a code interpreter (a tool for running code) would, and half wrote an R script that was then executed. The results bear on what executing code adds to an AI-assisted analysis, and on what researchers need to know of R to specify, read and check an agent’s code.

Development

Where the Variation Comes From

The sampling temperature sets how random the choice of each token is. A temperature of zero should select the most probable token at every step, but it does not make models served by their providers deterministic. Ouyang et al. (2025) asked ChatGPT at its default temperature to write code several times for each of 829 programming problems from three published sets with tests. For 47.56% to 75.76% of the problems, depending on the set, no two programs gave the same output on the problem’s tests, and a temperature of zero reduced that variation without removing it. Atıl et al. (2025) ran five such models 10 times on each of eight tasks with settings meant to be deterministic, and accuracy varied by up to 15 percentage points across runs.

He and Thinking Machines Lab (2025) traced much of this behaviour to the providers’ servers, where the number of requests processed together varies with demand. That number changes the order, and so the rounding, of some sums, enough to tip the choice between two almost equally probable tokens. With an open model, one that anyone can download and run, 1,000 replies to one request at temperature zero contained 80 distinct texts, and computations independent of that number brought them down to one. Anthropic (n.d.-b) states that results are not fully deterministic even at temperature zero, and its most recent models accept only the default temperature (Anthropic, n.d.-d).

Sampling is one source of variation among several. Providers can change proprietary models at any time (Spirling, 2023). Between the March and June 2023 versions of the two models behind ChatGPT, the accuracy of one of them at classifying numbers as prime or composite fell from 84% to 51% (Chen et al., 2024). Meaning-preserving changes in the format of a prompt, the text given to a model, altered the accuracy of one open model by up to 76 percentage points when the prompt included a few solved examples (Sclar et al., 2024). In a chat interface, none of these sources is under the user’s control, and few are recorded.

Choices Within the Researcher’s Control

Reproducibility with generative AI therefore rests on three choices left to the researcher: the tools, the requests made of them and the record of both. For the tools, McLoughlin et al. (2026) recommend open models, which can be run locally and so run again later, and, like Palmer et al. (2024), they ask that any use of a proprietary model be justified explicitly. An open model served by a company, however, may not match the published one. In summer 2024, 11 of 31 services offering Meta’s Llama models gave outputs whose distribution differed from that of the published model (Gao et al., 2025).

The choice extends to settings such as the effort level, which sets how many tokens a model spends on reasoning, text and tool use. Its default differs between models, and Anthropic (n.d.-a) advises setting it explicitly. The access route matters too, since a model may behave differently in a chat window and through an application programming interface (API), which lets other programs send it requests (Feuerriegel et al., 2026). So does the agentic tool around the model. Nadgir et al. (2026) report on 39 tasks from CORE-Bench, a benchmark that asks agents to reproduce published results from the studies’ code and data. At the same effort level, OpenAI’s GPT-5.4 solved 94.9% of them within Codex, the company’s own agentic tool, and 51.3% within CORE-Agent, an agent built for the benchmark.

The requests can ask for a script in place of an answer, one that runs without manual steps, prints the result in a fixed format and sets any random seeds. They can also ask for a file that pins package versions, and set out tests of the expected behaviour before the code is written, as Bridgeford et al. (2026) recommend. What the agents return still needs checking. Vangala et al. (2026) asked three coding agents for programs in Python, JavaScript and Java that would run in a clean environment, with every dependency and its version listed. Of the 300 programs, 205 ran without intervention, but none came with a lockfile fixing the version of every installed package.

Reporting guidelines set out the record. The GUIDE-LLM checklist asks authors in the behavioural sciences to report, among other items, the provider, the exact model identifier, the date of access, the access route, the settings and the prompts (Feuerriegel et al., 2026). Guidelines for software engineering add the version of the agentic tool, a trace of its tool calls (its actions, such as reading a file or running a command) and every setting, defaults included (Baltes et al., 2026).

Moving the Computation Into Code

Asking for a script brings AI-assisted work under the standards of reproducible computational research. These ask that every result be traceable to the steps that produced it, without manual data manipulation, and that the versions of external programs be archived (Sandve et al., 2013; see also Peng, 2011; Wilson et al., 2017). An agent’s script under version control documents the steps behind a result, but not the software environment, from the operating system to the package versions. When Trisovic et al. (2022) re-executed R files deposited with published research data, 75% of those that finished in the time allowed stopped with an error. After automatic fixes for problems such as missing packages and file paths that exist only on the original computer, 60% still did. The R package renv (Ushey & Wickham, 2026) reduces that risk with a lockfile that records the versions of R and of a project’s packages. With the output of sessionInfo(), the lockfile shows what has changed when a script behaves differently elsewhere.

The Simulated Data

The pilotr package generates data in R and in Python from a design specification written in JavaScript Object Notation (JSON), a plain-text format independent of any programming language. Because it uses the same random-number generator in both languages, and this specification rounds reaction times to whole milliseconds, the same specification and seed produce identical data in each (Bernabeu, 2026b). The specification below describes a balanced design in which 30 participants each respond to 24 words, once after a related prime and once after an unrelated one. Reaction times follow a lognormal distribution shifted to start at 250 ms, with a word-frequency covariate and with by-participant and by-word random intercepts and priming slopes.

The three checksums are identical, so the data set can be rebuilt byte for byte in either language. Because the data are simulated, the specification gives the population priming effect, and the code below estimates how much it varies across participants and across words by drawing a million of each.

fixed <- spec$fixed; random <- spec$random; frequency <- spec$predictors[[1]]
# effect_sd() below moves frequency with the word, so it must vary by word
stopifnot(frequency$name == 'frequency', frequency$varies_by == 'item')
mu <- fixed$intercept + fixed$coefficients$frequency * frequency$mean

# The variance, at a given prime code, of the terms that belong to one unit
# (participant or item): its random intercept and slope and their covariance.
unit_variance <- function(unit, prime_code) {
  unit$intercept_sd^2 + prime_code^2 * unit$slopes$prime_c^2 + 2 * prime_code *
    unit$intercept_sd * unit$slopes$prime_c * unit$correlations[['intercept,prime_c']]
}
residual_variance <- (fixed$coefficients$frequency * frequency$sd)^2 + spec$response$sigma^2

# The mean of a lognormal variable is exp(mu + variance / 2), and the shift
# cancels out of the difference between the two types of prime.
population_mean <- function(prime_code) {
  spec$response$shift + exp(mu + fixed$coefficients$prime_c * prime_code +
    (unit_variance(random$subject, prime_code) + unit_variance(random$item, prime_code) +
       residual_variance) / 2)
}
population_effect <- population_mean(0.5) - population_mean(-0.5)

# The priming effect of one participant (or word), averaged over the other
# unit and the residual, for a million simulated participants (or words). A
# word's frequency belongs to the word, so for words it moves with the word's
# intercept and is not averaged out.
effect_sd <- function(unit, other, word = FALSE) {
  z <- matrix(rnorm(2e6), ncol = 2)
  rho <- unit$correlations[['intercept,prime_c']]
  intercept <- unit$intercept_sd * z[, 1]
  slope <- unit$slopes$prime_c * (rho * z[, 1] + sqrt(1 - rho^2) * z[, 2])
  averaged <- residual_variance
  if (word) {
    intercept <- intercept + fixed$coefficients$frequency * frequency$sd * rnorm(nrow(z))
    averaged <- spec$response$sigma^2
  }
  unit_mean <- function(prime_code) exp(mu + intercept + prime_code * (fixed$coefficients$prime_c + slope) +
    (unit_variance(other, prime_code) + averaged) / 2)
  sd(unit_mean(0.5) - unit_mean(-0.5))
}

Every run received a description of the data and the same question: ‘How large is the priming effect, that is, how much slower are responses after unrelated primes than after related primes? Give the estimate in milliseconds with a 95% confidence interval.’ Each run had to end with a result line giving the estimate and the interval in a fixed format, so that code could compare the answers. The request was either open, leaving the analysis to the agent, or specified, naming the model, the contrast coding of the prime and the function that computes the interval. The data were either the balanced data set or, in a follow-up with the specified request, an unbalanced version from which 86 of the 1,440 trials had been removed at random. Its request said that incorrect responses had been removed. These three combinations of data and request are the conditions of the experiment.

In each condition, the runs followed one of two routes. In the prose route, the agent could read the data file but was told to run no code, to answer as in a chat without a code interpreter and, if it could not compute the answer exactly, to give its best estimate. In the script route, the agent wrote an R script, which it could run to check its work, and ended with a brief summary of what the script does. Its instructions named lme4 (Bates et al., 2015), lmerTest (Kuznetsova et al., 2017), emmeans and dplyr among the installed packages.

The prompts are kept in the experiment’s folder with the data, the scripts, each run’s final reply and a log of its tool calls, but not the agents’ full transcripts. The folder’s README explains how to download it on its own and repeat each step. Below is the specified request as one of the script runs received it. The open request lacks the paragraph beginning ‘Analyse the data as follows’.

Both rounds used the language model Claude Opus 5.5 (identifier claude-opus-5-5), with eight runs in each combination of condition and route. The first round ran on 29 September 2026 with Claude Code 2.1.284. Its 32 runs on the balanced data were launched eight at a time, in a random order across conditions. The 16 runs of the follow-up were launched afterwards, also in a random order.

In the first round, each agent ran in the background alongside others, with the model and effort level of the session that launched it, and was pointed to a folder of its own that held only the data file. The logs show that each prose run read nothing but its data file, and that 21 of the 24 script runs touched no file outside their own folder. The other three wrote exploratory R files under shared names such as explore.R to a temporary folder open to all the session’s agents. Each wrote and ran such a file within one command and read only its own data, so none appears to have run another’s code. One of them also read the output of a background R command from the session’s folder for such output. The first eight agents were launched from the experiment’s own folder, which holds the pilotr specification, and their logs show no access to it.

The session then executed each final script three times, each time in a fresh R process (as after restarting R) and a fresh copy of its folder. It also recorded the versions of R, lme4, lmerTest and Matrix, the package that lme4 uses for its matrix computations.

The second round ran on 11 October 2026 with Claude Code 2.1.295, from one session in the Claude desktop app on Windows 11. Its 48 runs were launched in the order of the first round, eight at a time, with those on the unbalanced data once 31 of the 32 on the balanced data had finished. Their prompts were the first round’s, except for each run’s folder and, in the script route, the version of R (4.6.1 in place of 4.3) and the full path of Rscript. Every agent ran at medium effort, as the transcripts record. Two runs on the balanced data, a prose reply to the specified request and a script for the open request, were also run at xhigh effort, the level above high, under the same conditions on the same day. No agent of the second round touched a file outside its own folder. The Results describe the first round unless they name the second.

# The numbers of each RESULT line as written, so that a reply's precision is

result_numbers <- function(line) {
  regmatches(line, regexec('estimate=(-?[0-9.]+) lower=(-?[0-9.]+) upper=(-?[0-9.]+)', line))[[1]][-1]

lowered <- function(deviation, runs) {
  lower <- rep(FALSE, length(deviation))

Given the open request, the eight scripts converged on one analysis, a linear mixed-effects model of the untransformed reaction times with crossed random effects for participants and words. The maximal model, with by-participant and by-word priming slopes, gave a singular fit, in which a random-effect variance is estimated at zero or a correlation at ±1. Its by-participant slope was perfectly correlated with the intercept, and every script dropped that slope. All eight then computed the interval from a t distribution with Satterthwaite’s approximation of the degrees of freedom, which lmerTest adds to models fitted with lme4 (Kuznetsova et al., 2017). Four also included word frequency as a covariate, although in a balanced design it cannot change the estimate, since every word appears after both types of prime.

Dropping the by-participant slope follows the parsimonious strategy that Matuschek et al. (2017) defend on the grounds of power, and sits uneasily with the maximal structure that Barr et al. (2013) recommend. The choice rested on the sample, as it must with real data. In this sample, the maximal model puts the standard deviation of the priming effect at 8.9 ms across participants and 29.8 ms across words, the reverse of the order in the population (18.3 and 12.9 ms).

The prose replies to the open request reached the same interval as the scripts by decomposing the 720 paired differences into participant, word and residual components. In a balanced design, this decomposition gives the same standard error as the scripts’ model without by-participant slopes. Five of these replies equated their decomposition with the maximal model, although that model keeps a small by-participant slope and gives a slightly wider Satterthwaite interval, [−1.78, 38.82] ms. With the specified request, both routes returned the Wald interval of the maximal model, which is narrower than either Satterthwaite interval because it takes its critical value from the normal distribution.

Every prose reply to the open request, and six of the eight summaries of its scripts, mentioned the narrower interval of a by-participant analysis. A paired t test over the participants’ mean differences gives [5.58, 31.46] ms, which excludes zero, and the same test over the words’ mean differences reproduces the open-request scripts’ interval, [−1.53, 38.57] ms. All of those replies and summaries set the by-participant analysis aside because it ignores how the effect varies across words and so overstates the evidence for generalising beyond the words sampled. The effect is real in this simulation, so that test reached the right conclusion by an analysis too liberal for the purpose. A test of the mixed models at the .05 level would have missed the effect, although their intervals contain its population value of 21.8 ms.

When the Design Is Unbalanced

In the unbalanced data, 84 participant-word pairs are left with a trial after only one type of prime and 1 with no trial at all. Without balance, the estimate of the mixed model, 21.79 ms in all eight scripts, no longer equals the difference between the mean reaction times after the two types of prime, 21.43 ms. Nor does the REML fit reduce to mean squares and cross-products, so it has to be found iteratively. Removing the trials moved the lower bound of the specified Wald interval from −0.74 to 0.58 ms, so that the interval no longer included zero. With Satterthwaite degrees of freedom, as in the open-request scripts, the same model gives [−0.57, 44.15] ms, which still includes zero.

The prose replies approximated the model with weighted averages of the per-word effects and estimates of the variance components from the observed mean squares. Unlike the replies to the specified request on the balanced data, each put the variance of the by-participant slopes at or near zero. The fit that lme4 found kept a by-participant slope with a standard deviation of 6.7 ms, perfectly correlated with the intercepts. The replies’ results therefore lie closer to those of the model without by-participant slopes, 21.85 [0.77, 42.92] ms, than to the executed result, which Table 3 sets beside them.

On the unbalanced data, the estimates lay near the mean difference over the 635 complete participant-word pairs, 22.98 ms, and the lower bounds well above the executed 0.58 ms. In every condition, the prose replies were faster than in the first round.

The two runs at xhigh effort returned the first round’s results, the script after 6.2 minutes and the prose reply after 11.2. The prose reply reconstructed lme4’s boundary fit and spent 11.0 minutes reasoning, against a median of 4.1 for the replies in its condition at medium effort.

Executing the Scripts Again

Executing a script again where it first ran tests whether it is deterministic, and executing it elsewhere tests whether its output depends on the environment. Every execution below ran in a fresh R process in the C locale, the minimal set of conventions for language and characters that every system provides. Outputs are compared through a checksum of their lines without the line endings, which Windows and Linux write differently. Between them, the scripts load dplyr, emmeans, lme4, lmerTest and tidyr, and lmerTest calls pbkrtest in the three open-request scripts that also report Kenward–Roger degrees of freedom. The Kenward–Roger method, an alternative to Satterthwaite’s approximation, also adjusts the standard error.

The first round’s 72 stored executions ran under R 4.3.3 on the Linux system Ubuntu 24.04.4 with lme4 1.1-35.1, lmerTest 3.1-3 and Matrix 1.6-5. Every script printed identical output each time, including its model summaries and warnings. Ubuntu 24.04 still offers those versions. A Dockerfile, a recipe from which the program Docker builds a packaged copy of an operating system and its installed software, rebuilds the environment from them, taking the other packages from a dated snapshot of the same release. Executed in that rebuild on a fresh machine provided by GitHub, all 24 scripts printed the stored output, as verification.csv records.

The 25 scripts of the second round were each executed twice, in the R library their agents had used, with R 4.6.1 on Windows, lme4 2.0-1, lmerTest 3.2-1 and Matrix 1.7-5. Each printed identical output both times, ending with the result line its agent had reported.

Discussion

What Executing Code Contributed

No text in this experiment was repeated, yet every executed script printed the same output each time it ran. Because the versions of R, lme4, lmerTest and Matrix were recorded and can still be installed, the first round’s scripts printed that output on another machine too. Under newer versions, their output changed only in formatting, in ways traced to lme4. The scripts also added exactness and a record that can be checked. On unbalanced data, which call for a numerical fit, every script returned the exact result and each prose reply an approximation. Even where the replies matched the scripts, only recomputing their quantities in R could tell a correct reply from a confident error.

Agreement between runs is a separate matter. On balanced data, it was complete in the first round. In the second, at medium effort, the prose replies to the balanced data gave seven different results and the open-request scripts two, whereas every script given the specified request returned the first round’s result. The close agreement of the first round contrasts with the large variation between runs of the same request that the studies reviewed above found in code generation and in accuracy (Atıl et al., 2025; Ouyang et al., 2025).

Many-analysts studies, which give one data set and one question to many teams, find wide variation among human analysts too. In one, the odds ratios of 29 teams ranged from 0.89 to 2.93 (Silberzahn et al., 2018). Autonomous AI analysts given one data set and one hypothesis also reached divergent verdicts in three domains, and their conclusions shifted with the language model and the prompt (Bertran et al., 2026). Alizadeh et al. (2026) ran Claude Code and Codex 20 times each on a many-analysts study of immigration and social policy. The agents varied their model specifications at least as much as the human teams had, but their estimates stayed broadly in line with the human consensus. The authors located the agents’ vulnerability in interpretation more than in estimation.

The task in this experiment was far simpler, with two types of prime, participants crossed with words and one obvious family of models. On unbalanced data, even the seven different results of the prose replies lay within 0.3 ms of one another.

Bertran et al. (2026) propose deploying AI analysts against a published specification to reveal how much disagreement comes from underspecified design choices. Here, the open request produced little disagreement in the first round, but in the second it divided the scripts over one random slope, which decided whether their interval excluded zero. The consistency of the first round belonged to one model, at one effort level, on one structured task, and may not survive the model’s next update (Chen et al., 2024). A study’s reproducibility therefore has to rest on what can be checked, such as a script and a record of its environment.

Why Direct Experience With R and an Integrated Development Environment Matters

The specified request is where the researcher’s knowledge entered the experiment. Writing it required knowing that the data call for crossed random effects, that the choice of random slopes changes the interval (Barr et al., 2013) and that transforming reaction times can change the effects being tested (Lo & Andrews, 2015). It also required knowing R, since the request names the function that fits the model, writes the model in the formula notation of lme4 and gives the call to confint() that computes the interval. Interpreting the output required knowing what a singular fit means.

The same request shows the limits of a specification. It fixed a Wald interval, which is too narrow with few participants or items (Luke, 2017). I chose it because one function call defines it exactly and so makes the scripts comparable, and on the unbalanced data that choice decided whether the interval excluded zero. An analysis for publication should request Satterthwaite or Kenward–Roger degrees of freedom, as computed in the open-request scripts. Across the two rounds, none of the 65 runs given the specified request mentioned either.

Reading the code is the second point of entry. The scripts in this experiment were 18 to 252 lines long, short enough for a researcher who reads R to confirm in a few minutes that each fits the intended model to the intended rows. In the first round, every summary of an open-request script reported dropping the by-participant slope and justified it by the fit of the maximal model. Weighing that justification against the chance that the effect varies across participants in the population, as it does in this simulation, takes knowledge the summary does not supply. In the second round, five scripts dropped the by-word slope as well, and three of their summaries stated that both slope variances were at or near zero. A reader of R would notice that each of these scripts skipped the model with only the by-word slope, and that every model they fitted with that slope put its standard deviation at about 30 ms. Without experience of R, the researcher is left with the agent’s summary of its own work, which is another text generated by the same language model.

Research on automation explains why that experience has to be maintained. Automation leaves its operators to monitor the system and to take over when it fails, while the skills needed for both decay without practice (Bainbridge, 1983). Complacency towards automation arises when other tasks compete for attention, occurs in experts as well as novices and is not overcome by simple practice (Parasuraman & Manzey, 2010). Studies of AI assistance point to similar risks. Among 319 knowledge workers surveyed, higher confidence in generative AI was associated with less self-reported critical thinking, and higher self-confidence with more (Lee et al., 2025). Developers who learned an unfamiliar software package with AI assistance scored lower on a later test of their understanding than those who learned without it, and were not significantly faster (Shen & Tamkin, 2026). Messeri and Crockett (2024) warn that AI tools can leave scientists believing they understand more than they do. For early-career researchers in particular, the ability to check an agent’s code has to be built by writing code.

An integrated development environment such as RStudio or Positron supports the writing of code and makes routine the checks this experiment needed. It shows the lines that each change adds or removes and those in which two outputs differ, works with version control, displays the objects in memory and can run a script again in a fresh R process.

A Reproducible Workflow With Coding Agents

The experiment illustrates a workflow built on the three choices reviewed above, beginning with the tools. Its model was proprietary, a choice that McLoughlin et al. (2026) suggest might be reasonable when, as here, the model itself is the object of study. Because the agents’ scripts were saved and executed, a later change to the model would affect only the scripts that it wrote afterwards. Where a language model processes the data itself, as in text annotation, its replies are the results, and a model whose version can be fixed, such as an open model run locally, is the safer choice (Palmer et al., 2024; Spirling, 2023).

With an analysis plan written before any code, ideally in a preregistration, every request can be a specified one. A prompt can also ask for the lockfile and tests reviewed above, such as a check that the code recovers the known parameters of data simulated with pilotr before it meets real data. Every script run was told to work only inside its own folder, yet 3 of the 24 in the first round wrote files elsewhere. The researcher therefore has to read each change before accepting it and, as was done here, execute each script again in a fresh R process.

The record should follow the reporting guidelines reviewed above (Baltes et al., 2026; Feuerriegel et al., 2026) and include the effort level. Here, the two runs at xhigh returned the first round’s results, which the same runs had not returned at medium effort. The project is under version control, and each script is saved with its outputs, a record of the environment, the prompts, the agent’s replies and a log of its tool calls.

Limitations

The experiment used one language model and one simulated data set, on which the lower bound of the interval for the priming effect lay close to zero. Its two rounds differed in date, in the version of Claude Code and in the system and the versions of R and lme4 that the agents worked with. Only two runs at xhigh link the differences between the rounds to the effort level, a link they suggest without establishing. With eight runs in each combination of condition and route, the counts describe these runs and do not estimate rates. The follow-up was designed after the first results on the balanced data. The specified request contained the model formula and the function for the interval, so the agreement among its scripts tested implementation more than analysis. The prose route imitated a chat without a code interpreter, although many chat assistants now have one. Its agents had no time limit and took up to 29 minutes per reply, so the route shows what prose replies can achieve with ample time.
