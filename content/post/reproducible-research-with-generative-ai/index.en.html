Ask a chat assistant the same statistical question twice, and you may get two different answers. A language model writes its reply one token, often a word or part of one, at a time, sampling each from a probability distribution (Holtzman et al., 2020). That matters now that generative artificial intelligence (AI) is used at many stages of research (Andersen et al., 2025). Reproducibility means obtaining consistent results from the same data, computational steps and conditions of analysis (National Academies of Sciences, Engineering, and Medicine, 2019, p. 46), and a reply in a chat window records few of those conditions.

Coding agents promise a way around this. Tools such as Claude Code can read a project, edit its files and run commands (Anthropic, n.d.-c). When such a tool writes an R script, the model’s variability enters while the script is being written. Once saved, the script can be read, tested and executed again, and given the same input, the same software environment and any random seeds it needs, it should return the same output.

I wanted to see how well that division of labour holds up, so I ran an experiment twice. In each round, 48 Claude Code agents received the same question about a semantic-priming data set that I had simulated with my pilotr package (Bernabeu, 2026b), so the true effect was known in advance. Half of the agents answered in prose, as a chat assistant without a code interpreter would, and half wrote an R script that was then executed. Some were left to choose the analysis, and the others followed one that I specified. The results show what executing code adds to an AI-assisted analysis, and which decisions a researcher still has to check.

Setting Up the Experiment

Before the experiment itself, it helps to see where the variation in a model’s replies comes from and which of its sources a researcher can control. The next two sections review both, and the two after them describe the data and the runs. The code behind every step is folded throughout the post and can be unfolded to inspect or reproduce it.

Why the Same Request Gets Different Replies

The obvious suspect is the randomness of sampling, which the temperature setting controls. A temperature of zero should select the most probable token at every step, yet it does not make the models that providers host deterministic. When Ouyang et al. (2025) asked ChatGPT for code several times per problem, the programs often gave different outputs, and a temperature of zero reduced that variation without removing it. Atıl et al. (2025) ran five models 10 times on each of eight tasks with settings meant to be deterministic, and accuracy still varied by up to 15 percentage points across runs.

He and Thinking Machines Lab (2025) traced much of this behaviour to the providers’ servers, where the number of requests processed together varies with demand. That number changes the order, and so the rounding, of some sums, which can be enough to tip the choice between two almost equally probable tokens. With an open model, one that anyone can download and run, 1,000 replies to one request at temperature zero contained 80 distinct texts, and computations made independent of that number brought them down to one. Models that reason before answering are especially exposed, since an early rounding difference can send the reasoning down another path (Yuan et al., 2025).

Sampling is only one source of variation. Providers can change proprietary models at any time (Spirling, 2023) and retire them, after which requests to them fail (Anthropic, n.d.-b). Between its March and June 2023 versions, GPT-4 fell from 84% to 51% accuracy in classifying numbers as prime or composite (L. Chen et al., 2024). Meaning-preserving changes to the format of a prompt, the text given to a model, altered the accuracy of one open model by up to 76 percentage points (Sclar et al., 2024). In a chat window, none of these sources is under the user’s control, and few are recorded.

What the Researcher Can Still Control

Reproducibility with generative AI therefore rests on three choices left to the researcher: the tools, the requests made of them and the record of both. For the tools, McLoughlin et al. (2026) recommend open models, which can be run locally and so run again later, and, like Palmer et al. (2024), they ask that any use of a proprietary model be justified. Even an open model may not match the published one when a company serves it. In summer 2024, 11 of 31 services offering Meta’s Llama models returned outputs whose distribution differed from that of the published model (Gao et al., 2025).

The choice of tools extends to their settings, such as the effort level, which sets how many tokens a model spends on reasoning, text and tool use, and whose default differs between models (Anthropic, n.d.-a). The second round of this experiment ran at medium effort. The access route matters too, since a model may behave differently in a chat window and through an application programming interface (API), which lets other programs send it requests (Feuerriegel et al., 2026). So does the agentic tool around the model. Nadgir et al. (2026) gave OpenAI’s GPT-5.4 39 tasks that ask agents to reproduce published results from the studies’ code and data. At the same effort level, it solved 94.9% of them within Codex, the company’s own agentic tool, and 51.3% within CORE-Agent, an agent built for the benchmark.

A request to an agent can ask for a script in place of an answer, one that runs without manual steps, prints its result in a fixed format and sets any random seeds. It can also ask for tests of the expected behaviour and a file that pins package versions, as Bridgeford et al. (2026) recommend. What comes back still needs checking. Vangala et al. (2026) asked three coding agents for programs that would run in a clean environment, with every dependency declared. Of the 300 programs, 205 ran without intervention, and on average, they used 15 times as many packages at run time as they declared.

Asking for a script brings AI-assisted work under the standards of reproducible computational research, which ask that every result be traceable to the steps that produced it and that the versions of the software be archived (Sandve et al., 2013; see also Peng, 2011; Wilson et al., 2017). A script kept under version control, in a system such as Git that records each version of a project’s files, documents the steps but not the software environment. When Trisovic et al. (2022) re-executed R files deposited with published research data, 75% of those that did not time out stopped with an error, and 60% still did after automatic repairs. The renv package (Ushey & Wickham, 2026) reduces that risk with a lockfile, which records the versions of R and of a project’s packages, and the output of sessionInfo() shows the environment that actually ran the code.

Reporting guidelines set out the rest of the record. The GUIDE-LLM checklist asks authors in the behavioural sciences to report the provider, the exact model identifier, the date and route of access, the settings and the prompts (Feuerriegel et al., 2026). Guidelines for software engineering add the version of the agentic tool and a trace of its tool calls, the actions it takes, such as reading a file or running a command (Baltes et al., 2026).

From the same specification and seed, pilotr produces identical files in R and in Python, at least for a specification such as this one, which rounds reaction times to whole milliseconds (Bernabeu, 2026b). fixed <- spec$fixed; random <- spec$random; frequency <- spec$predictors[[1]]
# effect_sd() below moves frequency with the word, so it must vary by word
stopifnot(frequency$name == 'frequency', frequency$varies_by == 'item')
mu <- fixed$intercept + fixed$coefficients$frequency * frequency$mean

# The variance, at a given prime code, of the terms that belong to one unit
# (participant or item): its random intercept and slope and their covariance.
unit_variance <- function(unit, prime_code) {
  unit$intercept_sd^2 + prime_code^2 * unit$slopes$prime_c^2 + 2 * prime_code *
    unit$intercept_sd * unit$slopes$prime_c * unit$correlations[['intercept,prime_c']]
}
residual_variance <- (fixed$coefficients$frequency * frequency$sd)^2 + spec$response$sigma^2

# The mean of a lognormal variable is exp(mu + variance / 2), and the shift
# cancels out of the difference between the two types of prime.
population_mean <- function(prime_code) {
  spec$response$shift + exp(mu + fixed$coefficients$prime_c * prime_code +
    (unit_variance(random$subject, prime_code) + unit_variance(random$item, prime_code) +
       residual_variance) / 2)
}
population_effect <- population_mean(0.5) - population_mean(-0.5)

# The priming effect of one participant (or word), averaged over the other
# unit and the residual, for a million simulated participants (or words). A
# word's frequency belongs to the word, so for words it moves with the word's
# intercept and is not averaged out.
effect_sd <- function(unit, other, word = FALSE) {
  z <- matrix(rnorm(2e6), ncol = 2)
  rho <- unit$correlations[['intercept,prime_c']]
  intercept <- unit$intercept_sd * z[, 1]
  slope <- unit$slopes$prime_c * (rho * z[, 1] + sqrt(1 - rho^2) * z[, 2])
  averaged <- residual_variance
  if (word) {
    intercept <- intercept + fixed$coefficients$frequency * frequency$sd * rnorm(nrow(z))
    averaged <- spec$response$sigma^2
  }
  unit_mean <- function(prime_code) exp(mu + intercept + prime_code * (fixed$coefficients$prime_c + slope) +
    (unit_variance(other, prime_code) + averaged) / 2)
  sd(unit_mean(0.5) - unit_mean(-0.5))
}

Each run received a description of the data and this question: ‘How large is the priming effect, that is, how much slower are responses after unrelated primes than after related primes? Give the estimate in milliseconds with a 95% confidence interval.’ It also had to end with a result line in a fixed format, so that code could compare the answers.

The request was either open, leaving the analysis to the agent, or specified, naming the model, the contrast coding and the function for the interval. Both came with the balanced data. A follow-up gave the specified request with an unbalanced version of the data, from which 86 of the 1,440 trials had been removed at random. Its prompt described them as incorrect responses that had been excluded. These make up the experiment’s three conditions.

Each condition had two routes. The prose agents could read the data but were told to run no code and to approximate where necessary, as a chat assistant without a code interpreter (a tool for running code) would have to. The script agents wrote an R script, could execute it to check their work and replied with a brief summary. Their instructions named lme4 (Bates et al., 2015), lmerTest (Kuznetsova et al., 2017), emmeans and dplyr among the installed packages.

The experiment folder holds the prompts, the data, the scripts, the final replies and the logs of the agents’ tool calls, with a README for repeating the work, although not the agents’ full transcripts. Both rounds used the language model Claude Opus 5.5 (identifier claude-opus-5-5), with eight runs in each combination of condition and route. The first round ran on 29 September 2026 with Claude Code 2.1.284. Its 32 runs on the balanced data were launched eight at a time, in a random order across conditions. The 16 runs of the follow-up were launched afterwards, also in a random order.

Each agent started in a folder of its own that held only its data file, and the logs show that the prose agents read nothing else. In the first round, however, 3 of the 24 script agents also wrote exploratory files outside their folders, although their commands show no sign of executing another agent’s code. Shared temporary folders, and for some agents the experiment folder itself, were within reach, so the isolation was imperfect, and the logs and the hidden checks on this page document each exception.

Each final script was then executed three times, each time in a fresh R process and a fresh copy of its folder. A record kept the versions of R, lme4, lmerTest and Matrix, the package that lme4 uses for matrix computations.

The second round ran on 11 October 2026 with Claude Code 2.1.295 on Windows 11. Its 48 main runs used medium effort and followed the first round’s launch order, eight at a time. Their prompts changed only the folder and, for the scripts, the version of R and the path to it. I added two runs on the balanced data at xhigh effort, a prose reply to the specified request and a script for the open request. No agent of the second round touched a file outside its folder.

# Pandoc sizes the columns of a wide table in proportion to the dashes under

column_shares <- function(table, shares) {
  separator <- grep('^\\|[-:|]+\\|$', table)
  cells <- strsplit(sub('^\\|(.*)\\|$', '\\1', table[separator]), '|', fixed = TRUE)[[1]]
  stopifnot(length(separator) == 1, length(cells) == length(shares), sum(shares) == 100)
  table[separator] <- paste0('|', paste0(ifelse(startsWith(cells, ':'), ':', ''), strrep('-', shares),
                                         ifelse(endsWith(cells, ':'), ':', ''), collapse = '|'), '|')
  table
}

# Dots closer than the gap, about the width of a dot, stack upwards, so that every run
# stays visible
stack_levels <- function(x, gap) {
  levels <- integer(length(x))
  for (i in seq_along(x)) {
    taken <- levels[seq_len(i - 1)][abs(x[seq_len(i - 1)] - x[i]) < gap]
    level <- 0L
    while (level %in% taken) level <- level + 1L
    levels[i] <- level
  }
  levels
}

What the Agents Chose When Left to Choose

Given the open request, the eight scripts converged on one analysis, a linear mixed-effects model of the untransformed reaction times with crossed random effects for participants and words. The maximal model, with by-participant and by-word priming slopes, gave a singular fit, one in which a random-effect variance is estimated at zero or a correlation at ±1. Its by-participant slope was perfectly correlated with the intercept, and every script dropped that slope. All eight then computed the interval from a t distribution with Satterthwaite’s approximation of the degrees of freedom, which lmerTest adds to models fitted with lme4 (Kuznetsova et al., 2017). Four also included word frequency as a covariate, although in a balanced design it cannot change the estimate, since every word appears after both types of prime.

Dropping that slope follows the parsimonious strategy of Matuschek et al. (2017) but sits uneasily with the maximal structure recommended by Barr et al. (2013). The sample suggested less variation across participants than across words, the reverse of the population pattern, so the agents faced the decision as an analyst would with real data, without the population values to go by.

The prose replies to the open request reached the same interval as the scripts by decomposing the 720 paired differences into participant, word and residual components. In a balanced design, this decomposition gives the same standard error as the scripts’ model without by-participant slopes. Five of these replies equated their decomposition with the maximal model, although that model keeps a small by-participant slope and gives a slightly wider Satterthwaite interval, [−1.78, 38.82] ms. With the specified request, both routes returned the Wald interval of the maximal model, which is narrower than either Satterthwaite interval because it takes its critical value from the normal distribution.

Every prose reply to the open request, and six of the script summaries, also considered a paired t test over participants, whose interval, [5.58, 31.46] ms, excludes zero. They set it aside because it ignores the variation across words and so overstates the evidence for generalising beyond the words sampled. The effect is real here, so that test would have reached the right conclusion, but through an analysis too liberal for the purpose. The mixed-model intervals include zero, and they also contain the population effect of 21.8 ms.

Mixed Models by Hand

An agent that ran no code could still fit a mixed model, and the prose replies to the balanced data showed how. Because every participant saw every word after both types of prime, the restricted maximum likelihood (REML) fit of the mixed model reduces to a few mean squares and cross-products of the paired differences and of their sums. Cross-products are the counterparts of mean squares for covariances. Table 2 recomputes in R the intermediate quantities that recur across the replies. Executing the Scripts Again

Executing a script again in the same environment tests whether it is repeatable, and executing it elsewhere tests whether it travels. Every execution below used a fresh R process in the C locale, a standard set of language and character conventions. Checksums compared the output line by line, allowing for the different line endings of Windows and Linux. The scripts use dplyr, emmeans, lme4, lmerTest and tidyr, and some also call pbkrtest for the Kenward–Roger method, which adjusts the standard error as well as the degrees of freedom.

The first round’s 72 stored executions used R 4.3.3 on Ubuntu 24.04.4, with lme4 1.1-35.1, lmerTest 3.1-3 and Matrix 1.6-5, and every script printed identical output each time. A Dockerfile rebuilds that environment from a dated snapshot of the software, and on a fresh machine on GitHub, all 24 scripts reproduced their stored output, as verification.csv records.

The second round’s 25 scripts were each executed twice in the library their agents had used, under R 4.6.1 on Windows. They too printed identical output, ending with the result each agent had reported.

What These Runs Can Establish

The experiment used one language model and one simulated data set, clean and fully described in the prompt, on which the lower bound of the interval lay close to zero. Real data bring exclusions, coding errors and gaps in documentation that these agents never faced. I designed the follow-up after seeing the results on the balanced data. The specified request also supplied the model formula and the function for the interval, so the agreement among its scripts tested implementation more than analysis. The prose route imitated a chat without a code interpreter, although many chat assistants now have one. An assistant that runs code and lets the researcher keep it could close much of the gap with a coding agent.

The two rounds differed in date, in the version of Claude Code, in the operating system and in the versions of R and lme4 that the agents worked with. The first round’s effort level, that of the session that launched it, went unrecorded, and only two runs were repeated at xhigh. The differences between the rounds therefore cannot be put down to the effort level alone. With eight runs in each combination of condition and route, the counts describe these runs and do not estimate error rates. Finally, I wrote every prompt as someone who reads R, so the experiment cannot show what a researcher without R would achieve with the same agents.

Discussion

What Executing the Code Added

No text in this experiment was repeated, yet every executed script printed the same output each time it ran. Because the versions of R, lme4, lmerTest and Matrix were recorded and can still be installed, the first round’s scripts printed that output on another machine too. Under newer versions, their output changed only in its formatting. The scripts also left a record of the calculation that no prose reply could supply. Even where a reply matched the scripts, only recomputing its quantities could tell a correct reply from a confident error.

A reproducible analysis can still be a poor one, however (Leek & Peng, 2015). The five scripts of the second round that dropped both random slopes printed identical output each time they ran. Their interval excludes zero and points the right way, because the effect is real in this simulation. With real data, nobody could know that. Leaving out a by-word slope when the effect varies across words makes a test too liberal (Barr et al., 2013), so the same analysis would claim an effect more readily where none existed.

Agreement between runs is a separate matter. Many-analysts studies, which give one data set and one question to many teams, find wide variation among human analysts (Breznau et al., 2022; Silberzahn et al., 2018). Autonomous AI analysts given one data set and one hypothesis also reached divergent verdicts that shifted with the language model and the prompt (Bertran et al., 2026). Alizadeh et al. (2026) ran Claude Code and Codex 20 times each on one of those many-analysts studies (Breznau et al., 2022). The agents varied their model specifications at least as much as the human teams had, yet their estimates stayed broadly in line with the human consensus. The authors located the agents’ vulnerability in interpretation more than in estimation.

The task in this experiment was far simpler, and the close agreement of the first round may reflect a shared preference as much as independent confirmation, since runs of one model are not independent analysts. When Herdağdelen et al. (2026) left Claude Opus 4.8 to make the five decisions of an analysis with no preference assigned to it, it made the same five choices in 112 of 123 runs. Forty-eight runs of one model that agree may amount to one opinion stated 48 times.

Bertran et al. (2026) propose giving AI analysts a published specification, to reveal how much of their disagreement comes from underspecified choices. Here, the specified request kept the scripts consistent across rounds, whereas the open request divided them over one random slope, which decided whether their interval excluded zero. That consistency belonged to one model, at one effort level, on one structured task, and it may not survive the model’s next update (L. Chen et al., 2024). What can be kept is the code and a record of its environment, and together they leave any such difference open to inspection.

Where Coding Literacy Comes In

By coding literacy, I mean being able to read and write code well enough to tell what a script does. The experiment did not vary it, but it shows where literacy came into the work, and at those points, much of what was needed turned out to be statistical knowledge.

Writing the specified request required knowing that the data call for crossed random effects, that the choice of random slopes changes the interval (Barr et al., 2013) and that transforming reaction times can change the effects being tested (Lo & Andrews, 2015). Coding came in only where the request named the function that fits the model, wrote the model in lme4’s formula notation and gave the call to confint() that computes the interval. I cannot say how much that helped, since no condition stated the same analysis in plain statistical language.

The same request shows the limits of a specification. It fixed a Wald interval, which can be too narrow with few participants or items (Luke, 2017), and I chose it because one function call defines it exactly and so makes the scripts comparable. On the unbalanced data, that choice decided whether the interval excluded zero. An analysis for publication should use Satterthwaite or Kenward–Roger degrees of freedom, as the open-request scripts did, yet none of the 65 runs given the specified request, in either round, mentioned either. On this point, the agents left to choose did better than my specification.

Reading the code is the second point of entry. The scripts were only 18 to 252 lines long, short enough for a researcher who reads R to confirm in a few minutes that each fits the intended model to the intended rows. In the second round, the summaries of three of the five scripts that dropped both slopes justified doing so by calling their variances zero or nearly so. A reader of R would notice that none of these scripts tried the model that drops only the by-participant slope. Printing the fits they discarded would also show that every model with the by-word slope put its standard deviation at about 30 ms. Without that reading, the researcher is left with the agent’s summary of its own work, which is more text from the same language model. Even so, what a reader would catch here is a statistical choice written in code, since no result pointed to a coding bug.

A reader of R is not the only possible remedy. Given the open request at xhigh effort, the one script I ran kept the by-word slope with nobody reading it. Three of the eight at medium effort did too, however, so this is only a hint that a setting may do part of a reader’s work. A second agent asked to review each script might do more, although runs of one model may share its preferences, and different models often err in the same way (Kim et al., 2025). The experiment did not test this.

Studies of how people use these tools complicate the picture. Anthropic, the maker of Claude Code, analysed about 400,000 sessions with it and concluded that the ability to steer the agent comes more from command of a domain than from the ability to write code (Hitzig et al., 2026). The authors call these findings preliminary, since the ratings come from a model’s reading of the transcripts and they cannot tell whether the code was used afterwards. In a randomised trial, 487 consultants at the firm BCG attempted data-science tasks outside their expertise, and those given ChatGPT outscored those given other resources. Among them, self-described competent coders came within about 5 percentage points of the firm’s data scientists on the coding and statistics tasks, whereas the group as a whole stayed 12 to 14 points below them (Wiles et al., 2026). Coding experience was not randomised, however, and the tool was a chat assistant.

Fluency in code does not guarantee independent judgement either. In another study from Anthropic, 50 professional analysts who regularly used R or Python carried out an analysis with Claude Code, whose preference on each decision had been secretly set by a coin flip. On four decisions between two reasonable options, they went with the agent’s preference 86% of the time, and in an exploratory analysis, neither experience nor expertise predicted who did so (Herdağdelen et al., 2026). The preferences were strengthened on purpose, so these figures may overstate everyday influence. The small group of less experienced analysts who chose to work without the agent made more serious errors, but because they chose for themselves, the comparison cannot isolate what the agent added.

Understanding is a further concern. In a small preprint, 54 computing students built a website, and those given a coding agent produced a better first version than those given a chatbot but understood it less well. With the agent, their background in code no longer predicted the quality of that version, but it still predicted their comprehension (Balepur et al., 2026). An agent may therefore mask differences in literacy without removing them. Developers who learned a software package with AI assistance likewise understood it less well, and they were not significantly faster (Shen & Tamkin, 2026).

Research on automation explains why this matters. Automation leaves its operators to monitor the system and to take over when it fails, while the skills needed for both decay without practice (Bainbridge, 1983). In a meta-analysis of 18 experiments, the more of a task that automation took over, the better performance was while it worked and the worse when it failed (Onnasch et al., 2014). Complacency towards automation arises in experts as well as novices (Parasuraman & Manzey, 2010). Knowledge workers more confident in generative AI also reported less critical thinking (Lee et al., 2025), and Messeri and Crockett (2024) warn that AI tools can leave scientists believing they understand more than they do. As agents improve, they give their supervisors fewer errors to catch, and so less practice at catching the ones that remain.

The evidence on learning is not uniform, since a meta-analysis of programming education found no reliable effect on exam scores, in either direction, when students could not use the tools in the exam (Maier et al., 2026). What the website and package studies show is that the quality of the output and the understanding behind it need assessing separately. For researchers in training, I would still advise learning to read and write R or Python, which for now is the most direct way to check an agent’s work. Study design, statistics and the habit of asking how a result could be wrong deserve at least as much of their time.

What Experts Expect From Coding Agents

This experiment captures one model on 29 September 2026 and 11 October 2026, and each of its runs wrote one short script. Longer projects add a problem that these scripts did not test, the upkeep of a growing codebase, from its documentation to its stale and duplicated files. Carlini (2026), who built a 100,000-line C compiler with 16 parallel agents, noted that ‘LLM-written code frequently re-implements existing functionality’ and assigned one agent to coalesce duplicate code and others to improve code quality and documentation. In SlopCodeBench, a benchmark in which agents repeatedly extend their own code, the code’s structure eroded in 77% of the runs, and quality guidance repeated at every step improved the starting point without slowing the decline (Orlanski et al., 2026). In open-source projects that adopted Cursor, an AI code editor, development sped up sharply but briefly, whereas static-analysis warnings and code complexity rose persistently (He et al., 2026).

The upkeep is improving, if unevenly. In SWE-CI, a benchmark in which agents maintain real repositories over many rounds of change, each provider’s newer models scored higher, although most models still broke previously passing tests in over three quarters of the tasks (J. Chen et al., 2026). In a research note from the organisation METR, maintainers reviewing patches from successive models saw the step from Claude 4 Opus to Claude 4.5 Sonnet improve mostly code quality (Whitfill et al., 2026).

Experts have not forecast how long researchers will need to read code to check an agent’s work, but their forecasts speak to a narrower milestone (Figure 4). In spring 2026, the Forecasting Research Institute asked its panels when a model would first succeed 80% of the time at tasks that take a human expert at least eight hours. The experts’ median forecast gave that milestone an even chance by 2030, and the superforecasters’ by 2028 (Forecasting Research Institute, 2026). Those dates concern completing tasks, however, and say nothing directly about when agents will keep a codebase healthy without supervision, or when researchers can stop reading code.

Measurements of past progress point the same way. By METR’s measure, the length of software task that frontier models can complete half the time doubled about every seven months between 2019 and 2025 (Kwa et al., 2025), and its update of January 2026 puts the doubling time since 2023 at about four months (METR, 2026a). That measure has limits of its own. It rests on self-contained tasks ‘with clear success criteria that can be automatically evaluated’ (METR, 2026b), and by METR’s account, relatively few of its tasks remain beyond the latest models (METR, 2026a). The health of a codebase, by contrast, can be scored only in part. Agents resolved fewer tasks when they built on code written by other agents than on code written by people, and many traditional measures of maintainability did not explain the difference (Patel et al., 2026).

Capability need not turn into use, either. The computer scientists Arvind Narayanan and Sayash Kapoor (2025) distinguish gains in capability from the development and adoption of reliable applications. They expect diffusion to stay slow in consequential settings, held back by institutions, tacit knowledge and the need for validation, and a growing share of people’s work to go into controlling AI. Upkeep illustrates their point, since whether a file is stale may depend on what its owner intends. Asked to ‘clean up old branches’, one agent issued a command to delete the branches on the remote server, although the user may have meant only those on their own computer (Hughes, 2026).

Whichever way these forecasts turn out, the case for saved and executed code would stand, since a script can be executed again whether or not anyone reads it. A well-kept codebase can still implement a poor analysis, and whether an effect should be allowed to vary across words depends on what a study means to generalise to, which no amount of tidying settles. Someone also has to answer for the result, which is why Nature decided in 2023 to accept no language model as a credited author (“Tools Such as ChatGPT,” 2023). In the meantime, the practical question is how to check the work that agents produce.

A Workflow for Research With Coding Agents

The experiment and the wider evidence point to a workflow built on the three choices reviewed at the start, the tools, the requests and the record, with checking and upkeep between them.

The tools come first, and their choice deserves a reason. I used a proprietary model because its behaviour was the object of study, a case in which McLoughlin et al. (2026) suggest that the choice may be reasonable (see also Palmer et al., 2024). Where a model’s replies are themselves the data, as in text annotation, a model whose version can be fixed, such as an open model run locally, gives a far stronger record (Spirling, 2023). With real data, the terms of consent and data protection also need checking before an agent sends anything it reads to a hosted model.

An analysis plan written before any code, ideally in a preregistration, allows every request to be a specified one, and the request can also ask for a runnable script, pinned dependencies and tests. Where a decision remains open, it may help to form a view before seeing the agent’s preference, or to ask it for the best case for each option, two approaches that Herdağdelen et al. (2026) suggest exploring.

Checking falls, for now, to someone who reads each change before accepting it and executes each script again in a fresh R process. That includes what the code does to files, since 3 of the 24 script agents of the first round wrote outside their folders. A growing project soon outruns any reader, and the checking then has to rest on independent reanalysis and on tests with many simulated data sets whose answers are known (Morris et al., 2019). One data set would not have been enough here, since both intervals of the second round’s open-request scripts contain the population effect (Figure 3), and only many data sets would show how often each misses it. Tests alone are not enough either. Maintainers of three open-source projects would not have merged roughly half of the patches by agents of 2024 and 2025 that had passed a benchmark’s tests, although those agents had no chance to respond to feedback (Whitfill et al., 2026).

The upkeep belongs in that review. After each substantial change, the documentation, stale files, inconsistencies and duplicated code all need a look. An agent can take on much of this work, as in Carlini’s project (Carlini, 2026), but asking it to may not be enough, since repeated guidance did not slow the decline in SlopCodeBench (Orlanski et al., 2026).

Finally, the record should include the effort level, alongside the versions of the model and the agentic tool, the settings, the prompts, the replies, the tool calls, the scripts and their outputs, and the software environment (Baltes et al., 2026; Feuerriegel et al., 2026). Having left the first round’s effort level unrecorded, I can only hint at its part in the differences between the rounds.

Used in this way, coding agents can make an AI-assisted analysis far more reproducible than a reply written without running code. Their summaries of their own work, however, are more text from the same model, so for now, the checking falls to a researcher who can specify, read and execute the code. How long that will hold is the least certain part of this post. That someone will have to answer for the result is among the most certain.
