Most literature searches are run twice. The first time, someone types a query into the Scopus website, exports a spreadsheet and starts screening. Months later a reviewer asks for the exact query, the date, the number of records returned by each database and the number of duplicates removed, and nobody can produce them, because nothing in the export records how it was made. Repeating the search through the application programming interface (API) has its own difficulties. Elsevier charges a weekly quota per request, offset paging stops at record 5,000, a large harvest interrupted at page 40 has to start again and the records arrive in a nested format that every laboratory reshapes in its own way.

I wrote the first version of the code behind this post as a set of scripts extending the rscopus package, which I described in 2024. The scripts grew into scopusflow, a package that separates describing a search from running it and that ships in two versions, one for R and one for Python, tested against the same fixtures. Nothing below contacts Elsevier, and no key is needed. Scopus records may not be redistributed, so the package bundles a complete harvest of 138 real journal articles on graphene supercapacitors, retrieved from OpenAlex in the format the package returns, and its test suite runs the harvest functions against a stand-in server that answers the package’s own requests from that corpus. The post uses the same device, so that every number in it comes from code that actually ran. Where the live API would be needed, the call is shown but not run, and a live example is in the companion post on speculation across scientific topics, whose searches this package now performs.

Writing the search before running it

A query in scopusflow is a character string that the API will receive verbatim, and the package builds it so that field tags and Boolean operators cannot be mistyped. The example is a review that I might plausibly run, on electroencephalography (EEG) studies of conceptual processing in learners of a third language.

q_cp  <- scopus_query('conceptual processing', 'EEG', .field = 'TITLE-ABS-KEY')
q_l3  <- scopus_query('third language', 'L3 learning', .op = 'OR',
                      .field = 'TITLE-ABS-KEY')
q_not <- scopus_query('python', 'snake', .op = 'AND NOT', .field = 'TITLE-ABS-KEY')
cat(q_cp, q_l3, q_not, sep = '\n')
#> TITLE-ABS-KEY(conceptual processing) AND TITLE-ABS-KEY(EEG)
#> TITLE-ABS-KEY(third language) OR TITLE-ABS-KEY(L3 learning)
#> TITLE-ABS-KEY(python) AND NOT TITLE-ABS-KEY(snake)

A search plan turns a query into a table of cells, typically one per year, with the page size set to the largest the API allows for the chosen view (200 records for the standard view, 25 for the complete view), since quota is charged per request. The plan is a plain object that can be printed, saved and put under version control before a single request is spent.

The same plan can already be written up. The report follows PRISMA-S, the extension of the PRISMA statement for reporting literature searches (Rethlefsen et al., 2021), and every item that the plan cannot know is stated as unrecorded. A report written at this stage is the protocol for the search.

cat(format(scopus_search_report(plan_l3), style = 'paragraph'))
#> The search described here has not been run. The search expression is TITLE-ABS-KEY(third language) OR TITLE-ABS-KEY(L3 learning), limited to publication years 2010 to 2025. It would be partitioned into 16 cells, one per year, each retrieved through the STANDARD view in pages of 200 records, under a paging mode chosen when the search is run. The PRISMA-S items this record cannot supply, among them peer review of the strategy, grey literature and any other database searched, remain yours to report.

Rerunning the same plan against the same cache costs nothing, and a smaller request is served trimmed from the complete checkpoints. The cap applies to each cell, so max_results = 5 over ten year-cells returns 50 records.

before <- stand_in$state$requests
httr2::with_mocked_responses(stand_in$handler, {
  again <- scopus_fetch_plan(plan, cache_dir = cache, resume = TRUE)
  few   <- scopus_fetch_plan(plan, max_results = 5, cache_dir = cache, resume = TRUE)
})
c(rows_again = nrow(again), rows_few = nrow(few),
  requests_spent = stand_in$state$requests - before)
#>     rows_again       rows_few requests_spent 
#>            138             50              0

A checkpoint records the query, the date range, the view and the page size under which it was written. A different plan pointed at the same directory is refused those checkpoints with a typed warning, and the records are fetched afresh, which is the intended behaviour, and the reason to give each plan its own cache directory.

other <- scopus_plan('graphene supercapacitor', years = 2015:2024,
                     field = 'TITLE-ABS-KEY', partition = 'year', page_size = 50)
n_mismatch <- 0L
httr2::with_mocked_responses(stand_in$handler, {
  withCallingHandlers(
    other_records <- scopus_fetch_plan(other, cache_dir = cache, resume = TRUE),
    scopus_warning_cache_mismatch = function(w) {
      n_mismatch <<- n_mismatch + 1L
      invokeRestart('muffleWarning')
    })
})
c(checkpoints_rejected = n_mismatch, records_refetched = nrow(other_records))
#> checkpoints_rejected    records_refetched 
#>                   10                  138

The 5,000-record ceiling

Offset paging in the Scopus API refuses any start position of 5,000 or more, so a query with more matches than that silently returns its first 5,000 records unless the client notices. scopusflow raises a typed warning when the ceiling is hit, and cursor paging goes past it. The ceiling is lowered to six records here to show both behaviours on the small corpus.

options(scopusflow.hard_cap = 6L)
httr2::with_mocked_responses(stand_in$handler, {
  capped <- withCallingHandlers(
    scopus_fetch('graphene supercapacitor', field = 'TITLE-ABS-KEY',
                 years = 2019, page_size = 5),
    scopus_warning_capped = function(w) {
      message(conditionMessage(w))
      invokeRestart('muffleWarning')
    })
  by_cursor <- scopus_fetch('graphene supercapacitor', field = 'TITLE-ABS-KEY',
                            years = 2019, page_size = 5, cursor = TRUE)
})
options(scopusflow.hard_cap = NULL)
c(offset = nrow(capped), reported = attr(capped, 'total_results'),
  cursor = nrow(by_cursor))
#>   offset reported   cursor 
#>        6       19       19

Merging the two sets with de-duplication is where the corpus shows one of its own limits. These records carry no Scopus identifier, so matching falls back to the DOI, and the 11 records without a DOI cannot be matched to their own copies. A live harvest carries an identifier on every record and returns each article once. The merged object records what was removed, which becomes item 16 of the PRISMA-S report later on.

A trend asks the API for one count per year and never retrieves a record, so it costs far less than a harvest, and a topic comparison counts, for each year, the records that mention a comparison term as a share of the reference literature. Through the stand-in, the comparison terms are matched against the corpus titles, so the shares below describe the bundled corpus, whose composition differs from that of the Scopus database.

httr2::with_mocked_responses(stand_in$handler, {
  trend <- scopus_trend('graphene supercapacitor', years = 2015:2024,
                        field = 'TITLE-ABS-KEY')
})
plot_scopus_trend(trend)

httr2::with_mocked_responses(stand_in$handler, {
  shares <- scopus_compare_topics(
    reference_query  = 'graphene supercapacitor',
    comparison_terms = c('flexible', 'laser', 'nitrogen'),
    years            = 2015:2024,
    field            = 'TITLE-ABS-KEY')
})
plot_scopus_comparison(shares, highlight = 'flexible')

The shaded band is a Wilson interval and the function’s documentation calls it an illustrative stability range rather than a confidence interval, since the API returns exact counts and nothing in them is sampled. A live comparison costs one request per term per year plus one per year for the reference, which for the nine topics and 47 years of the companion post comes to 846 requests, well within a weekly quota. The intersection of concepts is counted the same way, one request per row.

The write-up

The search record is produced from the objects alone. The plan, the per-cell accounting, the retrieval time, the package version and the paging mode all travelled with the harvest, so nothing is typed in by hand. Of the 16 PRISMA-S items, a harvest supplies five and a merge a sixth, and the remaining ten, such as the databases searched and the limits applied, are listed as the author’s to write.

The same record from Python

The Python package offers the same workflow over pybliometrics, with the same function names in snake case, and the two test suites pin the same rendering of the search record. Below, the fixture gives the bundled corpus the provenance that a live harvest would carry, renders the record and hashes it. The R and Python packages both hold this file as a golden test, and the pinned MD5 checksum is 56a132a18a4aa3b8a1097ac15342a5dd.

fixture <- example_records
attr(fixture, 'plan') <- plan
attr(fixture, 'retrieved_at') <- as.POSIXct('2026-07-22 09:15:00', tz = 'UTC')
attr(fixture, 'scopusflow_version') <- '0.3.0'
attr(fixture, 'paging') <- 'offset'
per_year <- as.integer(table(example_records$year))
attr(fixture, 'cell_totals') <- tibble::tibble(
  cell = 1:10, date = as.character(2015:2024),
  n_records = per_year, reported_total = as.numeric(per_year))
attr(fixture, 'combined') <- list(n_in = 149L, n_out = 138L, n_removed = 11L,
                                  deduplicated = TRUE)
golden <- scopus_search_report(fixture)
rendered <- paste0(format(golden, style = 'report'), '\n\n',
                   format(golden, style = 'paragraph'), '\n')
golden_path <- file.path(tempdir(), 'golden-search-record-R.txt')
con <- file(golden_path, open = 'wb'); writeLines(rendered, con, sep = ''); close(con)
unname(tools::md5sum(golden_path))

import hashlib
from datetime import datetime, timezone
import pandas as pd
import scopusflow as sf

records = sf.example_records()
plan = sf.SearchPlan('graphene supercapacitor', years=range(2015, 2025),
                     field='TITLE-ABS-KEY', partition='year')
per_year = records['year'].value_counts().sort_index()
records.attrs.update({
    'plan': plan,
    'retrieved_at': datetime(2026, 7, 22, 9, 15, tzinfo=timezone.utc),
    'scopusflow_version': '0.3.0',
    'paging': 'offset',
    'cell_totals': pd.DataFrame({
        'cell': range(1, 11), 'date': [str(y) for y in range(2015, 2025)],
        'n_records': per_year.values, 'reported_total': per_year.values.astype(float)}),
    'combined': {'n_in': 149, 'n_out': 138, 'n_removed': 11, 'deduplicated': True},
})
report = sf.scopus_search_report(records)
rendered = report.format(style='report') + '\n\n' + report.format(style='paragraph') + '\n'
print(sf.__version__, hashlib.md5(rendered.encode('utf-8')).hexdigest())

Only the reproduction snippet at the end of the Markdown record differs between the two languages, because it is code in the host language. A plan registered from R can therefore be rerun from Python, and the search reads identically when it is written up from either.

Running it live

With a key in the SCOPUS_API_KEY environment variable, the same objects go to the API. The comparison below, which produced the figures of the companion post, spends one count request per year for the reference literature and one per year for the comparison term.

scopus_compare_topics(
  reference_query  = '"linguistic relativity"',
  comparison_terms = 'speculat*',
  years            = 1980:2026,
  field            = 'TITLE-ABS-KEY')

The complete view pages at 25 records, eight times the requests of the standard view, and the abstract retrieval endpoint used by scopus_abstract() and scopus_corpus() draws on a separate, smaller weekly quota, one request per identifier. Both are reasons to size a plan with a count before running it, and to keep the checkpoints.
