# Website enhancements: changes made and proposals

Internal reference, November 2026. The first part records what the branch `claude/website-content-format-enhance-356y72` changes. The second part sets out further enhancements to consider before any of them is implemented. Nothing on the branch is deployed until it is merged into `master`, as long as the deploy workflow is not started by hand on the branch (its manual trigger accepts any branch).

## Changes on this branch

None of the changes touches an R Markdown source, its HTML output or its `_files` folder, so the deploy workflow has no post to rebuild. This also relies on no post being stale already, and the last deploy of `master` (run 343, which took 43 seconds, too short for the R steps) bears that out. Every built page was compared with a build of `master`. Three changes reach every page or a large set of pages: the menu (its order and the wording of the Resources tooltip), the Person structured data in every page's head, and the site description, which now reads 'Publications, software, presentations and tutorials on language, cognition, neuroscience, education, digital technologies, statistics and open science.' That description is the home page's meta description and also appears in the meta description of about 370 tag, category and publication-type pages, the 404 page and the authors index. Beyond these, only the home page, the author page, the four section lists, the publication, presentation and post feeds, the search index and the sitemap differ, and the sitemap only in the order of its 462 entries.

The home page now places Software after Workshops and Presentations, and the menu follows the same order. Section backgrounds alternate by position, so Workshops now has the grey background and Presentations the white one.

The texts on the home page and the section pages were revised for concision and house style. The bio merges six short paragraphs into four. It adds a sentence on part of the current work (children's reading comprehension in digital formats), drawn from the John Fell grant and the recent talks listed on the site, and it now names the LESS project and the role of local manager, taken from the experience entry. Both additions should be confirmed. The teaching section loses its generic phrasing ('cornerstone of scientific integrity', 'empowers students', 'cutting-edge', 'excel in their academic and professional endeavours') and several dangling modifiers. The courses keep their content, with two changes of wording to confirm: 'modularity versus holism' became 'modularity and holism', and 'business support services' became 'manufacturers' support services'. In the funding table, the Open Research Prize entry no longer says 'Awarded' for a shortlisting, and the John Fell entry no longer defines reading by what it is not. The section pages are now titled 'Publications', 'Presentations', 'Software' and 'Blog and Resources', each with a one-sentence subtitle, which also serves as the page's meta description in place of the site description prefixed by the title.

The largest gain in loading time came from the Videos section. A script wrapped each video entry in a `div` once the page had loaded, and moving an iframe in the document makes Chrome load it at once (Firefox and Safari were not tested), so all twenty YouTube players and the OSF viewer were requested on every visit to the home page, however far the visitor scrolled. The wrappers are now written in the Markdown, the rendered structure is identical, and the frames load only as the visitor approaches them. The tag network at the foot of the home page now reads the search index only when the visitor comes within about a screen of it, and it ignores hidden tags, which it had excluded only by accident of scroll position. The video thumbnail loads lazily and declares its size, so that it does not shift the page when it arrives. On first view, the page therefore no longer fetches the 221 KB search index or the 248 KB thumbnail, a saving of about 470 KB before compression, in addition to the twenty-one frames.

One CSS rule changed. In the home Software section, a negative margin clipped the last line of the longer citations ('(CRAN) and PyPI'). The same defect had been fixed for the blog list, and the software rule now shares that fix. The /software/ list and the home widget now both use Hugo's default order, as Hugo's sort function is not stable for items released on the same day. The Person structured data gains the avatar, the universities attended and the research areas, and the author page's meta description no longer begins with a colon.

`static/sw.js` now retires itself as a precaution. The old file was a service worker that served every same-origin script, stylesheet, font and image, and the pages whose paths contain /post/ or /publication/, from a cache that it never refreshed. Only `static/js/deferred-loader.js` and an unused backup partial contained code to register it, and the repository's full history shows no layout that ever loaded either, so the worker was probably never installed in any browser. If it was, the browser would have kept it, with frozen copies of those files, for as long as the file on the server stayed the same. The new version deletes the old caches and unregisters itself in any browser that holds it, and has no effect on any other. A test that registered the old worker, replaced it and triggered an update confirmed that the caches and the registration were removed.

## Proposals

### A grounded assistant for reading the research

An assistant that explains a paper to a visitor is feasible on this site, but only with safeguards that an off-the-shelf chatbot lacks, and the first step need not involve a live model at all.

The safest first step is a set of plain-language summaries, generated offline from the full text of each open-access paper, then checked, edited and approved before publication as ordinary text on the publication page, with a note on how they were produced (the podcast descriptions already carry one). This carries no risk of a fabricated statement reaching a visitor unchecked, costs nothing to serve, raises no privacy question and helps search engines. It needs a front-matter field such as `lay_summary` and a few lines in the publication layout to display it.

A live feature would add answers that no one has checked, so it should begin with a few bounded tasks offered as buttons (explain a term chosen from the paper, summarise the method, state the limitations the authors acknowledge), not a free-text box. Without free text, a visitor cannot steer the model with instructions of their own, and the privacy questions shrink. GitHub Pages cannot hold an API key, so the requests would go through a small proxy, for which a Cloudflare Worker is sufficient: its free plan allows 100,000 requests a day, and the time spent waiting for the model does not count towards its CPU limit ([Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits)). The page would send only the paper's identifier and the task, and the Worker would build the prompt itself, so that the endpoint cannot be used as a general relay to Gemini. A public endpoint can still be called by a script, which could exhaust the monthly budget and so take the feature down. A challenge such as Cloudflare Turnstile, a per-visitor rate limit and a spending limit counted by the Worker itself would be needed. I believe that a Google Cloud budget only sends alerts and does not stop spending by itself, but this should be checked.

The model would receive the full text of the one paper in question, never the open web, under instructions to answer only from that text and to say when the paper does not address the request. Instructions alone do not prevent fabrication, so the Worker should check each answer mechanically before a visitor sees it. The model would return its answer with the passages it relies on, through structured output, and the Worker would confirm that each passage occurs in the paper and that each cited reference appears in the paper's reference list. Both checks need normalised text on each side (hyphenation, ligatures, quotation marks and minus signs differ between a PDF's extracted text and a model's quotation) and a minimum length for passages, since a short phrase would match anywhere. The check catches quotations that are absent from the paper and references that are absent from its list. It does not catch a claim that its passages do not support, including the misreading of a statistical result or the misattribution of a finding to a genuine reference. For that reason, the interface would show the supporting passages under each answer. Hidden text in a publisher's PDF could also carry instructions to the model, which argues for using the author's own manuscripts, whose text is known.

The feature would also need to meet the standards of the rest of the site for accessibility: operable by keyboard, with focus moved sensibly and answers announced to screen readers.

The full texts used must be open access or author manuscripts that may be redistributed in this way, and a non-commercial or no-derivatives licence may limit what can be done with them. The terms of the Gemini API need checking at the source, as I could not open them while writing this note and search results disagree about the current wording. Some versions restrict apps offered to users in the UK, the EEA and Switzerland to the paid tier, and others apply the paid tier's data terms to unpaid use there ([Gemini API terms](https://ai.google.dev/gemini-api/terms); [forum discussion of the clause](https://discuss.ai.google.dev/t/clarification-on-only-paid-services-for-eea-ch-uk/107860)). Under the paid tier, Google states that it does not use prompts or responses to improve its products, although it logs them for a limited period. One version of the terms also excludes clients directed towards or likely to be accessed by people under 18, which this site is not, but the current wording should be confirmed.

On privacy, the Worker processes visitors' IP addresses for its rate limit, and Google receives the request and the paper, so both Cloudflare and Google act as processors. The privacy page would need to state the lawful basis (most simply, consent given by opening the assistant), the processors, the transfer of data to the United States and how long each keeps logs. Nothing should be sent until the visitor opens the assistant, as the site already does for Disqus, and a free-text box, if one were added later, would need a request not to type personal details.

The cost depends on the price per token at the time ([pricing page](https://ai.google.dev/gemini-api/docs/pricing)). Google's [token guide](https://ai.google.dev/gemini-api/docs/tokens) puts 100 tokens at roughly 60 to 80 English words, so a paper of 15,000 words comes to between 19,000 and 25,000 tokens, and the thesis to several times that. At an input price of $1.50 per million tokens, a thousand requests a month on articles would cost about $30 to $40, plus the answers. Explicit context caching charges much less per token for a paper that is sent repeatedly, but it adds an hourly storage charge, which at this level of traffic may exceed the saving. Implicit caching has no storage charge but helps only when requests about the same paper arrive close together.

Chrome's built-in model (Gemini Nano, through the Prompt API) would avoid the key, the cost and the transfer of data, but it runs only in desktop Chrome on capable hardware and downloads a large model on first use ([Chrome built-in AI APIs](https://developer.chrome.com/docs/ai/built-in-apis)). Posts on Chrome's developer forum from late 2025 and early 2026 put its input quota at 9,216 tokens, under half of a typical paper, though the figure is undocumented and has changed before ([chrome-ai-dev-preview-discuss](https://groups.google.com/a/chromium.org/g/chrome-ai-dev-preview-discuss)). It does not suit this purpose.

The recommended path is the reviewed summaries first, then, if they prove useful, a pilot of the bounded tasks on two or three open-access papers with the checks above in place.

### Robustness and accessibility

At every screen width, the profile details beside the photo (role, emails and profile icons) and every link in the tag cloud start invisible and appear only when a script reveals them on scroll. If JavaScript is off, or if jQuery fails to load from cdnjs, they stay invisible, as tests with scripts disabled and with cdnjs blocked confirmed. An outage at cdnjs would therefore hide the contact details. The hidden starting state should apply only once the script is known to be running, for instance under a class that the script adds to the page. This touches a shared block of CSS, so it was left for a separate change with visual checks, but it deserves priority over the other proposals in this note.

The grey of the section subtitles (`rgba(0,0,0,.54)` on white) gives a contrast of about 4.6:1, just above the WCAG AA threshold for normal text. A slightly darker grey would leave more margin.

### Loading time

Twenty YouTube frames still load as a visitor scrolls through the Videos section. A click-to-load placeholder (the video's thumbnail with a play button, which loads the player only when pressed) would remove that cost and keep YouTube from being contacted unless a video is played. This changes the section's markup and appearance, so it needs a decision on the design.

The site's main stylesheet (`academic.css`, compiled from the theme and `custom.scss`) is about 357 KB before compression and blocks rendering on every page. Much of it overrides earlier rules. Pruning it would help, but it needs page-by-page visual comparison, because the selectors depend closely on the structure of each page.

Font Awesome loads its full stylesheet and two font files (about 350 KB together before compression) for a few dozen icons. A subset served from the site, or inline SVG icons, would remove most of that. Serving Montserrat and Roboto from the site instead of Google Fonts would remove a third-party connection and the transfer of visitors' IP addresses to Google.

The 248 KB PNG video thumbnail would take about 50 KB as a JPEG or 29 KB as WebP (both at quality 80), and its transparency channel is unused. The featured images in the lists are produced at 150 pixels wide and shown at 150 CSS pixels, so they look soft on high-density screens. Adding a 300-pixel version through `srcset` would sharpen them at a small cost.

### Unused files and rules

`static/js/deferred-loader.js`, `performance-monitor.js`, `search-optimizer.js`, `ultra-performance.js`, `lazy-search.js` and `static/css/lazy-search.css` are referenced by no page, only by one another, and `PERFORMANCE_OPTIMIZATION.md` describes them as if they were in use. Removing these files and `PERFORMANCE_OPTIMIZATION.md` would leave the repository's account of its performance work accurate. `static/sw.js` should stay at its address (see above).

Several rules in `custom.scss` that address the Videos section (around lines 339, 344, 7974–7991 and 8013–8024) match nothing, because they describe the section's structure before the entries were wrapped, or because they look for `position: relative` with a space that the minifier removes. They matched nothing before this branch either, once the old script had run, so the videos display at 720 pixels on desktop. If a narrower video was intended, the selectors need to address `.multimedia-entry`. Otherwise, they can go.

### Content

The home page opens directly on the first publication, as the Publications heading is hidden on desktop, and the bio starts about 10,800 pixels down. A visitor arriving from a search engine sees the name in the menu bar but nothing on who Pablo Bernabeu is until they scroll a long way. One option is a single introductory line above the publications, linking to the bio.

The descriptions of the NotebookLM podcast episodes in the Videos section are labelled as generated, but phrases such as 'pervasive culture of silence' and 'structural paradox' read as generated text. Tightening them would bring them closer to the rest of the site. The abstract of the Gemini lightning talk ('democratises access', 'necessitates a shift in researcher responsibility') has the same quality, though it may need to remain as submitted.

The funding table names 'the readsync toolkit', which appears nowhere else on the site or in the CV. If it is the package now called lexsync, the entry should use the current name.
